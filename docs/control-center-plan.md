# Control Center — план разработки

Требования: `docs/control-center-requirements.md`. Панель — форк acp-ui (Vue 3 + TS + Pinia + Vite),
ветка `control-center`, всё состояние локальное (KV-стор), никаких бэкендов и внешних запросов.

## Схема работ

| # | Workstream | Требования | Исполнитель | Ветка / worktree |
|---|---|---|---|---|
| 0 | Оболочка: рейка Chat/Projects/Board/Dashboard, леджер активности, доки | F1, N* | Hermes (оркестратор) | `control-center` |
| 1 | Projects: проекты из рабочих каталогов, детальная панель, сессии, запуск новой сессии в проекте | F2, F8 | Hermes | `control-center` |
| 2 | Board: канбан (7 колонок, карточки с критериями приёмки), вкладки Agents/Locks/Timeline/Events | F3, F4 | Devin CLI, `swe-2-max` | `cc/board` (worktree `acp-ui-cc-board`) |
| 3 | Dashboard: расходы/токены по агентам-проектам-дням, лимиты с квотами, экспорт | F5, F6 | Pi CLI, `zen-relay/muse-spark-1.3-contributor-free` | `cc/dashboard` (worktree `acp-ui-cc-dash`) |
| 4 | Приёмка: сборка, E2E playwright по всем трём экранам, скриншоты, слияние, отчёт | N10 | Hermes | — |

## Контракты, зафиксированные до старта (чтобы агенты не конфликтовали)

- **Файлы-владельцы.** У каждого workstream свой набор файлов: Devin правит только
  `src/components/BoardView.vue` + `src/features/board/**` + `src/stores/board.ts`; Pi —
  `DashboardView.vue` + `src/features/dashboard/**` + `src/stores/limits.ts`. Общие файлы
  (`App.vue`, `stores/session.ts`, `stores/activity.ts`, `stores/ui.ts`) каждый агент обязан
  считать чужими: нужна правка — писать запрос в `REPORT.md`, а не лезть в файл.
- **Единый источник данных — леджер.** `src/stores/activity.ts` уже собирает факты из протокола
  (`usage_update` с токенами и стоимостью, старт/конец хода, tool-calls, блокировки сессий,
  ошибки) и отдаёт агрегаты по агенту/проекту/дню. Оба воркстрима читают только его, поэтому
  дашборд и вкладки доски не тянут данные каждый по-своему.
- **Дизайн-язык.** Только токены из `App.vue :root` (плюс тёмный блок), плоско, хайрлайны, без
  теней и градиентов, без эмодзи в роли иконок (stroke-SVG в `currentColor`), машинный текст —
  моно, плотные строки, строки UI — английские.
- **Верификация — не отчёт, а вывод команд.** Каждый агент обязан прогнать
  `npm run build:web` (vue-tsc + vite) и свой playwright-E2E по собранному бандлу, а результат
  вставить в `REPORT.md`. Приёмка Hermes-ом — независимая: сборка ветки, E2E-скрипт заново,
  скриншоты на 1440/1024/390, диff-ревью.
- **Ограничения.** Никаких новых рантайм-зависимостей (графики — свой SVG), никаких сетевых
  вызовов, `systemctl` не трогать, тестовые серверы — только на портах 25998/25999.

## Порядок слияния и приёмки

1. Дождаться обоих агентов (Devin — доска, Pi — дашборд), проверить `REPORT.md`, `git log`
   ветки и реальность E2E-вывода.
2. Влить `cc/board` и `cc/dashboard` в `control-center` (ожидаемые конфликты: только в
   `App.vue`, если агент всё же его тронул; решать в пользу варианта из `control-center`).
3. Собрать бандл, прогнать заново все E2E (`e2e_shell_projects.py`, `e2e_board.py`,
   `e2e_dashboard.py`) на одном и том же снимке — у одного агента скрипт мог проходить на его
   ветке и падать после слияния.
4. Деплой: `npm run build:web` → `dist-web/` (его раздаёт `acp-ui-web.service`), проверить
   живьём на `http://192.168.1.222:25808` — четыре экрана, три вьюпорта.
5. Скриншоты в `docs/`, затем отчёт: что сделано, чем доказано, что осталось, какие запросы
   интеграции не выполнены.

## Риски и как они закрыты

- **Разные агенты правят один файл** → распределение владения файлами выше; общие сторы
  принадлежат оркестратору и уже готовы.
- **Агент «рассказывает», а не проверяет** → каждому запрещено отчитываться без вывода команд;
  приёмка повторяется Hermes-ом на своей стороне.
- **Параллельные прогоны на одном рабочем каталоге** → отдельные git worktrees на ветках
  `cc/board` и `cc/dashboard`, `node_modules` подключён симлинком.
- **Ручные подтверждения в Hermes душат автоматику** → вся тяжёлая работа отдана внешним CLI
  (`devin -p --permission-mode dangerous`, `pi -p`), Hermes только пишет брифы, собирает и
  проверяет.
- **Ночной прогон «уплывает»** → у обоих брифов явный приоритет: сначала рабочий минимум с
  зелёной сборкой, остальное — пометкой `PARTIAL` в отчёте.

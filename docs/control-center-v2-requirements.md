# Control Center v2 — проекты-как-папки, проектный скоуп, канбан-конвейер

Дополняет/пересматривает `control-center-requirements.md` и `control-center-roles-requirements.md`.
Источник: правки владельца от 2026-09-23.

## A. Проекты — это просто папки (пересмотр F2)

- **Проект = папка.** Список проектов настраивается в **Settings → Projects** (админ-раздел):
  - создать папку по указанному пути (mkdir через host-абстракцию),
  - или указать путь к уже существующей папке.
- **Ссылки GitHub/GitLab пока НЕ поддерживаем** — папку можно создать вручную и попросить агента
  склонить. (Решение владельца: «не надо пока усложнять».)
- Поля проекта: `{ id, name, path, defaultAgent? | defaultRole?, notes }`.
- **«Чат без проекта» = проект `Common`** с широкой общей папкой (создаётся автоматически).
  Кнопка «New session» без выбранного проекта стартует сессию в `Common`.

## B. Глобальный скоуп «текущий проект» (пересмотр F1)

- В шапке — **селектор проекта** со значением **All** + список проектов.
- Он скоупит: список сессий, вид Projects, канбан, (опционально) дашборд. Выбор проекта = фильтр:
  показываются только сессии/карточки, связанные с этим проектом.
- **Сессии по проекту**: при входе в проект слева открывается старый полный список сессий
  (тот вид, что был до переделки UI), отфильтрованный по этому проекту. «Выбор проекта просто
  срабатывает как фильтр» — дословно из ТЗ.

## C. Канбан-конвейер (пересмотр F3)

Колонки = **стадии**. У карточки есть `stage` (колонка) и `status` внутри стадии
(`in_progress | review | done`; у `Backlog` и `Done` внутреннего статуса нет / он терминальный).

| # | Стадия (колонка) | Что происходит | statuses внутри | Роль |
|---|---|---|---|---|
| 1 | **Backlog** | сырые идеи, может быть только заголовок | — | — |
| 2 | **Spec** (проработка) | идея обрастает мясом: чёткие границы (что делаем/не делаем), функциональные и нефункциональные требования | in_progress → review → done (review пройдено → done, нет → обратно in_progress) | spec-роль |
| 3 | **Plan** (планирование) | план разработки: сколько субагентов, какие модули, corner cases | in_progress → review → done | planner-роль (умная модель) |
| 4 | **Dev** (разработка) | карточка переезжает сюда; подзадач нет — одна карточка, даже если её делают несколько субагентов | in_progress → review → done | dev-роль |
| 5 | **Review/Test** (тестирование) | сначала агент тестирует, затем приёмка человеком (= финальное тестирование) | in_progress (агент тестирует) → agent_tested → accepted (человек) → карточка уходит в Done | tester-роль + человек |
| 6 | **Done** (выполнена) | терминальная | — | — |

- **Канбан фильтруется по проекту** и привязан к выбранному проекту (селектор из §B): сначала
  выбираем проект, потом видим его доску; есть кнопка **All** — увидеть все карточки сразу.

## D. Роли (F9) — привязка к стадиям

Роли из `control-center-roles-requirements.md` остаются, но привязываются к **стадии и/или статусу**
внутри неё (не к произвольной колонке). Зафиксированные решения владельца:

- промпт роли — **файлом в рабочем каталоге проекта** (`ROLE.md`/`AGENTS.md`), inline — fallback;
- **роль-ревьюер пока не делаем** (позже); авто-переход в `done` запрещён;
- **автономный прогон = автоматический режим без запроса прав** (auto-approve), всё авто-разрешённое
  пишется в аудит.

Остальные пункты (claim+lease+heartbeat, одна карточка = одна сессия, handoff-блок, evidence,
лимиты/стоимость по роли, изоляция worktree, ручные заметки, счётчик отскоков, видимая очередь и
расход) — из `control-center-roles-requirements.md` (F9.4–F9.18, N11–N20), без изменений.

## E. Миграция существующей доски

Старые семь колонок → новая модель:

- `inbox` → **Backlog**
- `ready` → **Spec** (status `in_progress`)
- `blocked` → **Backlog** с пометкой `blocked` (рекомендация: сделать это флагом карточки, не колонкой)
- `active` → **Dev** (status `in_progress`)
- `review` → **Review/Test** (status `in_progress`)
- `done` → **Done**
- `cancelled` → **Done** с пометкой `cancelled` (или архив)

Существующие карточки не теряются; персистенция получает `version`-миграцию (старая `board.json`
читается и раскладывается по новой схеме).

## F. Решения владельца (2026-09-23, зафиксированы)

1. **`blocked`/`cancelled` — флаги карточки** внутри стадий (пометки, не отдельные колонки и не
   статусы). Карточка в любой стадии может нести флаг `blocked` (причина) или `cancelled`; такие
   карточки визуально помечаются и не участвуют в автозаборе.
2. **Дашборд скоупится по выбранному проекту**, с кнопкой **All** (та же логика, что у канбана).
3. **Проект `Common`** (чат без проекта) создаётся по умолчанию и указывает на **`~/projects`**.

## F10. Роль `pm` — менеджер проекта (добавлено 2026-09-23)

Задача владельца дословно: «когда я по проекту добавляю карточки, они могут противоречить друг другу
или блокировать друг друга — нужен агент-менеджер проекта, который будет следить за тем, как карточки
связаны между собой, не пересекаются ли, не противоречат ли, не блокируют ли друг друга».

- **F10.1 Природа роли.** `pm` — не исполнитель: он **никогда** не делает работу по карточке, только
  анализирует граф карточек проекта и предлагает связи/правки. Роль такая же связка
  `{executor, model, prompt-файл}`, как остальные; модель можно дешёвую, но с большим контекстом.
- **F10.2 Что ищет PM** (по всем карточкам проекта, включая Backlog):
  1. **Противоречия** — две карточки требуют взаимоисключающего поведения;
  2. **Пересечения** — трогают одни и те же модули/файлы (риск конфликтов при параллельной работе);
  3. **Блокировки** — одна карточка логически требует другую сделанной раньше;
  4. **Дубликаты** — по сути одна и та же работа.
- **F10.3 Данные, без которых PM работать не может** (добавить в карточку): список затрагиваемых
  модулей/путей `touches[]` и явные связи `dependsOn[]` / `blocks[]` / `conflictsWith[]` (массивы id
  карточек). Поля необязательные — PM их заполняет и уточняет сам, человек правит.
- **F10.4 Выход PM-прогона** (в порядке приоритета):
  1. связи на карточках (`dependsOn`/`blocks`/`conflictsWith`) — **авто-применяются**,
     с записью в аудит и видимыми бейджами (`blocked by #12`, `conflicts #7`);
  2. флаг `blocked` с причиной у карточки, которая ждёт другую — авто, но с возможностью снять вручную;
  3. заметка-отчёт на карточке («пересекается с #7 по модулю X») — как комментарий агента, не правка;
  4. предложение изменить scope/статус — **только предложение**, применяет человек (никаких
     разрушительных автоправок).
- **F10.5 Триггеры.** Вручную кнопкой «Проверить связи» в шапке доски (прогон по выбранному проекту);
  автоматически — с дебаунсом (например, не чаще одного прогона на N минут и только когда карточки
  менялись), чтобы PM не жёг токены на каждый чих. Прогон не блокирует исполнителей.
- **F10.6 Видимость.** Результат PM-прогона виден: бейджи связей на карточках, отчёт в леджере
  (Events), панель «Связи» на доске — список конфликтов/блокировок с переходом на карточки.
- **N21. PM не ломает состояние.** Если прогон упал, превысил лимит стоимости или вернул мусор —
  доска остаётся ровно такой, какой была; частичные правки не применяются (атомарность по прогону).
- **N22. Лимит стоимости прогона** у роли `pm` (как у любой роли, F9.15) + запись расхода в дашборд.

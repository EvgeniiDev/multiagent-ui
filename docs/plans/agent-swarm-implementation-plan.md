# Четвёртая поставка: Swarm

Решения согласованы: 2026-09-30. План сохранён: 2026-10-01.
Основание: [общий план](agent-execution-plan.md), [исследование Swarm](../research/4shygray/swarm-roy-agentov.md).

## Основа агентов: настроенные профили Pi

Согласовано 2026-10-01: постоянная архитектура — Pi как одна базовая среда агента и отдельные конфигурации ролей. Подготовка идеи, разработка, панелист, судья, интегратор и проверяющие роли запускают подходящий Pi-профиль с заранее установленными навыками/расширениями/инструментами. Поддержка этих фич сразу во множестве разных CLI не требуется. Разные профили — конфигурации одного harness, а не обязательное множество продуктов. Модели/provider/effort задаются явно и могут различаться; минимум двух разных моделей Fusion сохраняется.

AgentProfile содержит profileId/version, закреплённую версию Pi, provider/model/effort, skills и их версии, extensions/tools, системные инструкции, права и лимиты. Начальная проверенная версия Pi — установленная 0.85.1; профиль сохраняет её и digest ресурсов до запуска. Пакеты/ресурсы готовятся заранее, не устанавливаются из пользовательского prompt во время задачи. Профиль и навыки заменяются настройками; универсальный перевод workflow во все CLI не входит в работу.

Использовать отдельный PI_CODING_AGENT_DIR и HOME/каталог сессий для каждого participant attempt; неизменяемый шаблон профиля общий, writable session state отдельный. Pi поддерживает явные --skill/--extension, отключение автоматического discovery и --tools allowlist. Проектные extensions/settings по умолчанию не доверяются; не загружать их молча поверх выбранного профиля. Проверить, что вызов через porch сохраняет нужные profile flags/env; если wrapper мешает, добавить минимальную поддержку Pi-профиля вместо трёх универсальных адаптеров. Профиль задаёт инструменты, но реальные файловые/сетевые ограничения по-прежнему обеспечивает среда.

Интерактивность подготовки — Pi RPC и собственное расширение ACP UI: вопросы, документы, skill gates и пользовательские ответы через поддержанные RPC/extension-UI события. Плагинные исходники не патчить; нужны инструменты и их семантика в расширении Pi. Совместимость каждого нужного workflow проверяется реальным probe; перенос текста SKILL.md сам по себе не доказательство. Базовый процесс, роли и согласования принадлежат ACP UI; не строить отдельный universal SkillRunner для произвольных CLI.

Эта поправка действует для четырёх новых планов. Текущую реализацию ядра в другом чате не переписывать: её существующий process-runtime и legacy CLI остаются совместимыми, выбранные будущие роли используют Pi profiles. Реальные проверки новых режимов выполняются на участвующих профилях Pi, а не требуют запуска Devin/Codex.

## Goal Capsule

Равноправные участники выполняют общую цель в одном worktree, согласуют решения и не перезаписывают чужие файлы. Начинать после ядра, [Fusion](agent-fusion-implementation-plan.md) и [оркестратора](agent-orchestrator-implementation-plan.md). Среда Fusion переиспользуется; запуск оркестратора не является обязательной стадией каждого Swarm.

Не выпускать Swarm с одним лишь промптовым запретом правок: ограничения общего дерева и чужих файлов должны подтверждаться реальными проверками.

## Product Contract

### Summary и Problem Frame

Общий проект сокращает задержку передачи изменений, но создаёт гонки записи. Равноправным агентам нужны координация, владение файлами, сообщения и ограниченные циклы работы.

### Requirements

- **R1 — общая цель.** Участники получают принятые документы, одну цель и позывные. Модельного руководителя нет; сервер обеспечивает протокол.
- **R2 — координация.** До реализации правки запрещены. Каждый объявляет часть цели, файлы, контракты, подход и риск. Реализация разрешена после явного согласования распределения и разрешения пересечений. Тишина не означает согласие.
- **R3 — один владелец.** Файлом владеет один участник. Остальные передают ему предложение правки или договариваются о передаче владения между ходами. Для передачи нужно явное согласие владельца и получателя; исключение — команда пользователя после подтверждённой остановки потерянного владельца.
- **R4 — серверные правки.** Общее worktree доступно участникам ro. Правки подаются через acp-run, проверяются сервером и применяются от имени участника. Проверяются фаза, владение, версия, пути и симлинки; создание/удаление/переименование также. Прямые shell-правки общего дерева запрещены технически.
- **R5 — сообщения и решения.** Адресные/общие сообщения, предложения и обязательные решения. Решение вступает в силу после явного подтверждения всех затронутых участников. Решение по общему API/типам затрагивает всех участников; по одному файлу — его владельца и заявленных потребителей. Расширение круга участников отменяет прежнюю готовность решения до новых подтверждений.
- **R6 — ходы.** Одна локальная цель на ход, максимум 10 минут. Между ходами участник получает текущие изменения, обязательные решения и непрочитанные сообщения. Native resume не требуется: новый вызов получает durable контекст. Доставка внутрь занятого CLI не требуется.
- **R7 — тупики и лимиты.** До трёх раундов координации, до 12 рабочих ходов на участника, до трёх раундов догона. Тупик передаётся пользователю с вариантами и последствиями; независимая работа продолжается. Изменение требований/плана требует отдельного согласования, пользовательское решение спора не обходит этот гейт.
- **R8 — восстановление.** Сообщения, владение, команды и результаты сохраняются. Пропавший участник не теряет владение автоматически; сначала подтвердить terminal старой попытки, затем восстановить или передать права. Повтор команды не применяет правку второй раз.
- **R9 — готовность.** После реализации и догона — общие проверки, reviewer/checker ядра и приёмка конкретного результата. Неразрешённые обязательные решения/блокирующие замечания не позволяют принять запуск.

### Key Decisions

- **KD1 — один владелец файла** (session-settled: user-directed — вместо владения участками). Governs R3, R4.
- **KD2 — тупик решает пользователь** (session-settled: user-directed — вместо арбитра-модели или остановки всего роя). Governs R7.
- **KD3 — ограниченные ходы по 10 минут** (session-settled: user-directed — вместо 3/20 минут). Governs R6.

### Scope Boundaries

Совместное интервью/написание требований, live interrupt всех CLI, параллельное владение участками файла и автоматическое слияние основной ветки не входят.

## Planning Contract

### Key Technical Decisions

- **KTD1 — роли и фазы.** Run.mode=swarm, coordinate/implement/catch_up и гейты ядра. Владение, сообщения и решения принадлежат запуску. Сервер валидирует протокол; модель не может выдать себе права текстом ответа.
- **KTD2 — полномочия.** acp-run использует scoped participant token и отдельный command relay из worker-среды. Token привязан к runId/participantId/attemptId/turnId и поколению полномочий; разрешает только сообщения, подтверждения, заявки/передачи и правки активной попытки в допустимой фазе. При terminal/deadline/stop её полномочия отзываются; новый ход получает другое поколение. Уже принятую durable apply-операцию восстанавливать по журналу независимо от отзыва, не принимать новых команд старого хода. Административные команды, общая доска, чужие артефакты и execution API недоступны. Токен не в логах; отзыв после stop запрещает новые правки. Запрос apply во время stop отклоняется или завершается как уже начатая durable операция до фиксации terminal.
- **KTD3 — рабочие материалы.** Общее дерево ro, включая Git-метаданные: worker не может git reset/checkout изменить его. После координации выдать отдельную scratch-копию для подготовки diff; это не владение общим деревом. Проверки полного проекта выполняются на серверной копии текущего результата, а не в произвольной scratch-копии агента.
- **KTD4 — broker правок.** Принимать структурированный набор файловых операций с commandId, expectedContentHash каждого файла, версией владения и полными новыми байтами/ссылкой на собственный artifact. Вместе с hash проверять ожидаемые тип и Git mode файла. Поддержать только 100644/100755: существующий mode сохраняется по умолчанию, владелец может явно изменить executable bit, включая chmod-only операцию; произвольные chmod/setuid не поддерживать. Для отсутствующего файла — отдельный expected absent. Права проверять на всех затронутых путях. В v1 менять только обычные файлы; symlink/gitlink и пути .git отклонять. Rename требует владения source и reservation destination. Владение нового пути резервируется до create; владение каталога не даёт права на его файлы.
- **KTD5 — пути и транзакции.** Один broker-writer на worktree, команды сериализуются. Worktree-level barrier охватывает apply и start/resume всех читателей: до первой записи зафиксировать transaction ID, durable список identities worker и подтверждённый freeze каждого; новые reader/ходы до снятия barrier не стартуют. Пока freeze не подтверждён полностью, файлы не менять. Отклонять абсолютные пути, traversal и symlink-компоненты; проверять через directory handles/no-follow, а не только string prefix. Транзакция хранит intent, предыдущие и новые hashes/байты, типы и Git modes и результат. До commit recovery завершает/откатывает по журналу, затем выпускает одно событие. Во время apply/recovery worker-чтение останавливается через контроллер; следующий ход видит целиком применённый снимок. После рестарта держать барьер закрытым до восстановления журнала; по сохранённым identities разморозить либо подтвердить завершение только принадлежащих worker. Stop/deadline сначала завершает/откатывает транзакцию, затем обеспечивает thaw для обработки porch cancel и ждёт terminal. При невозможности recovery остаётся blocked с диагностикой, новые читатели не допускаются. Не обещать атомарность multi-file операции одним rename.
- **KTD6 — сообщения и snapshot.** У сообщений последовательный cursor; доставка в следующий durable prompt фиксирует границу и IDs. Обработка решения — отдельное явное подтверждение неизменяемой ревизии, включающей текст/hash и список затронутых участников, не автоматический ack доставки. Изменение текста или состава создаёт новую ревизию без переноса прежних подтверждений. Позднее подтверждение старой ревизии сохраняется в истории, не делает новую обязательной. Перед ходом синхронизировать scratch с текущим снимком и вернуть сохраняемые непереданные предложения; stale hash при apply возвращает конфликт без скрытого слияния.
- **KTD7 — ограниченный scheduler.** Ход завершается ответом либо подтверждённой отменой на deadline; следующий не стартует при неизвестной живости предыдущего. Участник с тупиком ждёт pending decision, независимые продолжаются. Общий run blocked только после отсутствия исполнимой работы. Продление лимита требует явной команды пользователя и сохраняется в истории.

### Assumptions и Defaults

Два участника, две попытки роли, три цикла исправления; лимиты R6/R7 и глобальная concurrency редактируются до запуска и сохраняются. Во время обычных ходов сервер принимает правки сразу; чужие изменения гарантированно передаются перед следующим ходом. Техническое замораживание worker-процессов вокруг короткого apply не считается новым рабочим ходом. При недоступном механизме freeze/snapshot режим блокируется, без небезопасного fallback.

## Implementation Units

### S1 — Сообщения, решения, владение

**Covers:** R1–R3, R5, R7, R8; KTD1–KTD2. **Зависимости:** ядро, Fusion, оркестратор.
**Files:** server/execution/swarm/; scripts/test_swarm_protocol.mjs (новый).

Добавить типы Message, Proposal, Decision, FileOwnership и ролевые команды. Затронутые участники фиксируются сервером с учётом области решения; разногласие блокирует принятие.
**Сценарии:** две заявки на файл дают одного владельца; silence не approve; передача во время активного хода отклоняется; global decision требует всех; решение пользователя сохраняет согласования документов; foreign/stale token отклоняется; команда/сообщение/подтверждение прошлого хода отклоняется после старта нового, включая reviewer-fix; изменение текста решения между подтверждениями и поздний ack старой ревизии не дают общего согласия.

### S2 — Broker и durable применение

**Covers:** R3, R4, R8; KTD2–KTD5. **Зависимости:** S1.
**Files:** server/execution/swarm/, scripts/acp-run; scripts/test_swarm_edits.mjs (новый).

Реализовать валидацию, журнал, сериализацию, recovery и worker freeze/snapshot. Добавить команды submit/apply_result и структурированную диагностику конфликтов. Broker сам коммиты не публикует; snapshots и итоговая ветка обслуживаются ядром.
**Сценарии:** ранняя/чужая правка; stale hash; create/delete/rename; коллизия rename; .git, traversal, симлинки и TOCTOU; duplicate commandId с тем же/другим payload; crash до/во время/после multi-file записи и до события; повтор не даёт вторую правку; stop во время apply не оставляет частичный результат; start/apply race блокирует новых читателей; crash после freeze/commit/до thaw восстанавливает identities и освобождает принадлежащие контейнеры; stop/deadline frozen worker подтверждается terminal; chmod-only, создание executable, сохранение mode и rollback.

### S3 — Ходы, координация и догон

**Covers:** R1, R2, R5–R9; KTD6–KTD7. **Зависимости:** S2.
**Files:** server/execution/swarm/, prompts/execution/swarm/; scripts/test_swarm_scheduler.mjs (новый).

Подключить ro-профиль worker, scratch, канал команд, сохранённые prompts/курсор, таймауты, раунды и гейты ядра. В verify/review/awaiting_acceptance broker отклоняет новые правки. Замечания назначаются затронутым владельцам; для исправления сервер явно возвращает run в implement/catch_up и разрешает запись только назначенным участникам. Межфайловые изменения согласуются протоколом решений. Ходы исправления учитываются в общих лимитах; при исчерпании ждать явного продления пользователем. Каждая правка аннулирует готовность снимка и требует повторных общих проверок/reviewer/checker. Не запускать новый ход до сверки старой попытки.
**Сценарии:** завершение координатора не требуется; участники явно принимают распределение; новые сообщения приходят в следующем ходе; timeout отменяется до новой попытки; restart не теряет cursors/ownership; исчерпание 12 ходов и трёх раундов; зависшая попытка не теряет ownership; независимые продолжаются при споре; финальные проверки инвалидируются новой правкой; замечание к двум владельцам возвращается им; исчерпанный владелец ждёт продления; broker отклоняет правки в фазах проверки/приёмки.

### S4 — UI, реальные обходы и выпуск

**Covers:** R1–R9. **Зависимости:** S3.
**Files:** карточка/managed Workflow и stores; scripts/e2e_swarm.py, scripts/swarm_environment_smoke.mjs (новые).

Показать позывные, фазы, ходы/лимиты, файлы владельцев, обсуждения, решения и действия пользователя. Токены и внутренние пути не показывать.
**Сценарии:** пользователь решает тупик; перенос файла; 409 из второй вкладки; stop/continue; попытки shell/git/API/сети обойти broker каждым Pi-профилем; совместимость legacy/внешнего Workflow.

## Verification Contract

Детерминированные S1–S3 с fake runtime, временным Git и crash-injection журнала. Реальный Compose-backed прогон двумя участниками; Участвующие Pi-профили отдельно подтверждают запрет обхода и полный lifecycle. Browser S4; npm run build:web на хосте. Проверить claims, review и ACP-инварианты.

## Definition of Done

S1–S4 и R1–R9 доказаны. Прямые/чужие/преждевременные правки отклоняются технически, восстановление журнала не дублирует изменения, участники получают актуальные решения, пользователь видит тупики/лимиты. Общий результат проходит гейты и приёмку. Экспериментальный код удалён; merge/push отдельно.

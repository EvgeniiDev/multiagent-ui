# Подготовка идеи: от обсуждения до принятого плана

Дата: 2026-10-01. Продуктовые решения согласованы в разговоре; технические решения и defaults ниже — предлагаемый способ их реализации. Возможности ещё не реализованы.
Основание: [roadmap](agent-roadmap.md), [контракт ядра](agent-core-implementation-plan.md).

## Основа агентов: настроенные профили Pi

Согласовано 2026-10-01: постоянная архитектура — Pi как одна базовая среда агента и отдельные конфигурации ролей. Подготовка идеи, разработка, панелист, судья, интегратор и проверяющие роли запускают подходящий Pi-профиль с заранее установленными навыками/расширениями/инструментами. Поддержка этих фич сразу во множестве разных CLI не требуется. Разные профили — конфигурации одного harness, а не обязательное множество продуктов. Модели/provider/effort задаются явно и могут различаться; минимум двух разных моделей Fusion сохраняется.

AgentProfile содержит profileId/version, закреплённую версию Pi, provider/model/effort, skills и их версии, extensions/tools, системные инструкции, права и лимиты. Начальная проверенная версия Pi — установленная 0.85.1; профиль сохраняет её и digest ресурсов до запуска. Пакеты/ресурсы готовятся заранее, не устанавливаются из пользовательского prompt во время задачи. Профиль и навыки заменяются настройками; универсальный перевод workflow во все CLI не входит в работу.

Использовать отдельный PI_CODING_AGENT_DIR и HOME/каталог сессий для каждого participant attempt; неизменяемый шаблон профиля общий, writable session state отдельный. Pi поддерживает явные --skill/--extension, отключение автоматического discovery и --tools allowlist. Проектные extensions/settings по умолчанию не доверяются; не загружать их молча поверх выбранного профиля. Проверить, что вызов через porch сохраняет нужные profile flags/env; если wrapper мешает, добавить минимальную поддержку Pi-профиля вместо трёх универсальных адаптеров. Профиль задаёт инструменты, но реальные файловые/сетевые ограничения по-прежнему обеспечивает среда.

Интерактивность подготовки — Pi RPC и собственное расширение ACP UI: вопросы, документы, skill gates и пользовательские ответы через поддержанные RPC/extension-UI события. Плагинные исходники не патчить; нужны инструменты и их семантика в расширении Pi. Совместимость каждого нужного workflow проверяется реальным probe; перенос текста SKILL.md сам по себе не доказательство. Базовый процесс, роли и согласования принадлежат ACP UI; не строить отдельный universal SkillRunner для произвольных CLI.

Эта поправка действует для четырёх новых планов. Текущую реализацию ядра в другом чате не переписывать: её существующий process-runtime и legacy CLI остаются совместимыми, выбранные будущие роли используют Pi profiles. Реальные проверки новых режимов выполняются на участвующих профилях Pi, а не требуют запуска Devin/Codex.

## Goal Capsule

Пользователь приносит сырую идею в карточку и в одном разговоре с ведущим получает конкретные требования, проработанное решение и согласованный план, готовый для передачи в solo, Fusion, оркестратор или Swarm. Небольшая задача проходит короткий процесс, сложная — более глубокий. Исходники внешних навыков не меняются, навыки можно заменять.

Планировать и реализовывать фичу отдельно от трёх групповых режимов. Базовый входной гейт — завершённое ядро U1–U7 с документами, согласованиями и управлением карточкой. Fusion нужен только для дополнительной явно выбранной проверки документа; автоматически его не запускать. Порядок релизов групповых режимов остаётся Fusion → оркестратор → Swarm. Точная календарная позиция подготовки идеи относительно них не является требованием фичи.

Слияние, публикация и старт реализации не являются результатом подготовительного разговора. Передача принятых документов делает кнопку запуска доступной, но сама её не нажимает.

## Product Contract

### Summary и Problem Frame

Сырая идея обычно не содержит всех сценариев, ограничений и критериев. Запуск нескольких полных плагинных процессов подряд повторяет интервью и теряет принятые решения. Нужен единый процесс ACP UI с одним ведущим, общей памятью и заменяемыми навыками.

### Requirements

- **R1 — весь путь.** Из карточки бэклога начать обсуждение идеи; уточнить намерение, функциональные требования, продуктовые/технические варианты и план разработки. Требования содержат пользователей, сценарии, правила, ограничения и проверяемые критерии; план содержит изменения, зависимости и проверки.
- **R2 — один ведущий.** Пользователь общается с одним ведущим агентом и одним связанным обсуждением. Подключение навыка не начинает повторное интервью и не создаёт отдельное пользовательское окно. Результаты вспомогательных проверок возвращаются через ведущего.
- **R3 — адаптивность.** Не задавать обязательное число вопросов и не прогонять все плагины полностью для каждой задачи. Ведущий оценивает достаточность во время обсуждения; маленькая задача проходит краткое уточнение, сложная — дополнительные раунды и сравнение вариантов.
- **R4 — переход по достаточности.** Ведущий сам завершает текущую прожарку, когда ясны цель, пользователи, сценарии, ограничения, критерии и существенные решения, а блокирующие вопросы закрыты. Он показывает документ, предположения и явно отложенные вопросы; пользователь читает, принимает или возвращает замечания. Уверенность модели сама по себе не согласование.
- **R5 — два согласования.** Требования и план принимаются отдельно по versionId/hash. Дизайн отдельным документом нужен только при существенных вариантах/рисках; в простом случае решения входят в план. Отдельное обязательное согласование дизайна в базовом процессе не добавлять, но обязательные гейты выбранного навыка сохранять и проверять в готовности. Гейты intent/design предъявлять пользователю как отдельные подтверждения конкретного результата; не подделывать их выполнение и не считать approvals другого документа выполнением этих гейтов.
- **R6 — преемственность.** Сохранять ответы, принятые решения, обоснования, ограничения, предположения, вопросы и связь с версиями документов. После закрытия вкладки или смены CLI-сессии разговор продолжается с этим контекстом. История обсуждения — источник доказательств, текущий снимок решений — вход следующего этапа.
- **R7 — изменение намерения.** Новый ответ, меняющий требования, создаёт новую версию и аннулирует согласование старого плана по правилам ядра. Комментарий или вопрос о статусе сам по себе не меняет принятые документы. Пользователь видит причину возврата к этапу и что требуется пересогласовать.
- **R8 — заменяемые навыки.** Superpowers, Compound Engineering и Grill Me являются начальными источниками навыков, а не обязательными доменными типами. Пользователь может назначить другой совместимый навык этапу. Исходники установленных плагинов не менять; обновления поставщиков не требуют слияния локальных патчей.
- **R9 — явная совместимость.** Перед подключением проверить доступность навыка, ссылок на его ресурсы, нужных инструментов и возможностей CLI. Нельзя выдавать краткую текстовую имитацию за исполнение навыка. Неизвестный/несовместимый навык отображается с причиной; пользователь выбирает совместимый навык или явно обычную работу ведущего без навыка.
- **R10 — контроль.** Пользователь может продолжить обсуждение, попросить документ раньше, вернуть замечания или остановить. Ранний документ помечает незакрытые вопросы и не становится принятым автоматически. Остановка сохраняет состояние и документы; старый ответ остановленной попытки не заменяет текущую версию.
- **R11 — передача.** После принятия требований и плана карточка предоставляет ядру их версии, необязательный дизайн, критерии и согласованные команды проверки. Реализация доступна только при действительных согласованиях и совместимом составе. Состояние готовности относится к документам, а не к качеству будущего кода.

### Key Decisions

- **KD1 — законченный путь до плана** (session-settled: user-directed — вместо только уточнения идеи/требований). Governs R1, R11.
- **KD2 — один ведущий** (session-settled: user-directed — вместо ручного переключения отдельных разговоров). Governs R2, R6.
- **KD3 — внешние навыки без локальных патчей** (session-settled: user-directed — ради обновления и замены плагинов). Governs R8, R9.
- **KD4 — адаптивная глубина** (session-settled: user-directed — вместо полного процесса для любой задачи). Governs R3, R4.
- **KD5 — ведущий определяет переход, пользователь принимает результат** (session-settled: user-approved — вместо согласования момента остановки каждого интервью). Governs R4, R5, R10.

### Acceptance Examples

- **AE1:** небольшая правка → ведущий уточняет существенное, предлагает короткие требования; после принятия готовит короткий план без обязательного отдельного дизайна.
- **AE2:** крупная новая функция → дополнительные вопросы и сравнение вариантов, отдельный дизайн при необходимости, затем согласованный план без потери ранних ответов.
- **AE3:** после принятия плана пользователь меняет правило поведения → новая версия требований, прежний план не готов к реализации до обновления/пересогласования.
- **AE4:** внешний навык обновился → начатая подготовка не переключается на новую версию молча; пользователь видит несовместимость/вариант обновления.

### Scope Boundaries

Фича готовит задачи разработки ПО в зарегистрированных проектах. Самостоятельная проверка рыночных гипотез интервью/экспериментами, произвольные коннекторы, автоматический запуск всех моделей и изменение исходников плагинов не входят. Fusion может проверять документ отдельным явным запуском; Swarm и оркестратор здесь не используются для подготовки документов. Существующие карточки с готовыми документами могут сразу использовать ядро, без обязательного интервью.

## Planning Contract

### Key Technical Decisions

- **KTD1 — ACP UI владеет процессом.** Добавить PreparationSession, связанную с карточкой и обсуждением, и фазы clarify/requirements/design/plan/ready. При этом lifecycle запущенных попыток и DocumentVersion/Approval переиспользуются из ядра. PreparationSession не является implementation Run и не получает claim реализации. Одна активная подготовка на карточку; две вкладки не создают двух ведущих.
- **KTD2 — ведущий и транспорт.** Использовать существующий слой CLI/ACP и обсуждение карточки; обеспечить перенос контекста, prompt, события, вопросы и отмену выбранного Pi-профиля через RPC/расширение ACP UI. Автономный porch delegate сам по себе не является поддержкой интерактивного навыка: перед каждым вызовом передавать сохранённые ответы и checkpoint, вопрос отдавать в чат с durable questionId/attemptId и типом транспорта. Native UI-диалог сохраняет RPC request ID; answer_question доставляет extension_ui_response с matching ID действующей попытке, а не очередной prompt. Вопрос, которым уже завершён ход, получает ответ в следующем prompt. После потери процесса восстановить вопрос из checkpoint с новым RPC ID; старый ответ не отправлять чужой/остановленной попытке. Повтор answer_question идемпотентен, восстановленный ответ не исполняет SkillGate повторно. Недоступный инструмент навыка реализовать с проверенной семантикой в расширении Pi либо блокировать этот workflow; универсальные adapters других CLI не нужны.
- **KTD3 — контракт навыка.** SkillBinding содержит назначение этапа, provider/resource reference, digest версии, adapter version, требуемые возможности и способ получения результата. Интеграционный слой ACP UI готовит контекст, загружает оригинальные ресурсы навыка, переводит поддержанные вопросы/результаты/гейты в протокол подготовки и импортирует документы. Название плагина не становится phase или document kind. Adapter не переписывает инструкции навыка и не отменяет его явные гейты.
- **KTD4 — обновления.** Binding и полный набор используемых ресурсов фиксировать для подготовки с hashes. При доступной копии закреплённой версии продолжать её; при исчезновении/изменении ресурсов приостановить только вызов навыка. Пользователь может явно обновить binding: новая версия и событие миграции, checkpoint сохраняется, зависимые черновики переоцениваются, прежние approvals не переносятся на изменённый текст. Новые подготовки используют текущую конфигурацию.
- **KTD5 — начальные профили.** Предлагаемый default: Grill Me interview-me для намерения, grilling при существенных нерешённых развилках; Compound ce-brainstorm для требований/вариантов и ce-plan для плана; Superpowers brainstorming как альтернативный профиль проработки архитектурного дизайна. Не прогонять два brainstorming подряд автоматически. Все три набора являются кандидатами registry; доступными считаются только доказанные P0 route/capability combinations. Superpowers architectural требует настоящий spec commit и его подтверждение, затем writing-plans в document workspace; это цепочка одного binding, а не незаметная замена обязательного handoff на ce-plan. Bounded/spike routes, ведущие сразу к реализации либо не выдающие требуемого плана, не включать в начальные совместимые bindings подготовки без отдельного доказательства разрешённого исходным навыком перехода. CE durable использует реальные документы и doc-review в document workspace; lightweight/chat результаты импортируются как draft и передаются отдельному этапу плана. Конкретная задача использует только нужные доказанные bindings. Default — предложение реализации, а не требование пользователя применять каждое название.
- **KTD6 — вопросы и доказательства.** Сохранять структурированный checkpoint с решениями, provenance, открытыми вопросами и ссылками на сообщения/документы. Вопросы навыков остаются данными, не административными командами ACP UI. План/требования валидировать по обязательным полям, связям и версиям; LLM-оценка достаточности не заменяет backend validation и пользовательское approve. Ресурс навыка не получает право запустить реализацию, git commit/push или внешнюю публикацию.
- **KTD7 — документы и разрешения.** Работа подготовительных ролей с проектом — чтение; generated documents сохраняются в execution storage через scoped API, не произвольные пути целевого проекта. Для навыков, которым нужны реальные документы и Git, выделить автономный writable document workspace с приватным Git, а целевой проект предоставить отдельно ro. Разрешённые docs_root, CONCEPTS и выходные файлы относятся к document workspace; оригинальный CONCEPTS целевого проекта при наличии читается как вход, обновлённая версия сохраняется в document workspace. Записи/коммиты происходят реально только там; filesystem paths доступны проверяющим ролям. Импорт в DocumentVersion не является фиктивным ответом на файловую операцию. Перед применением адаптером этого размещения проверить предусмотренное исходным навыком переопределение путей/контекста. Если оно несовместимо с route, binding блокируется. Команды проверки становятся структурированными предложениями для подтверждения в плане, а не запускаются из текста навыка. Если контракт CLI не даёт требуемых ограничений, документная фича не получает writable fallback. Read-only среда F1 Fusion переиспользуется при её наличии; её обязательные гарантии должны быть реализованы/доказаны до выпуска подготовки, если она поставляется раньше Fusion.
- **KTD8 — API и UI.** Расширить API карточки командами start_preparation, answer_question, request_draft, continue_discussion, stop_preparation, change_skill_binding. Каждая содержит commandId и ожидаемую управляющую ревизию. Approve requirements/plan, attach_document и start реализации использовать из ядра. Выбор binding в настройках, отдельные пользовательские действия в чат-карточке; никаких plugin-specific статусов доски.

### Assumptions и Defaults

Один ведущий, явные CLI/модель, адаптивный процесс. Новые bindings выбираются из зарегистрированных/проверенных ресурсов; произвольный remote URL не выполняется автоматически. Вспомогательная многомодельная проверка не включена по умолчанию. Таймауты и retries берутся из состава ядра; ожидание ответа человека не является зависанием или исчерпанием времени вызова CLI. Контрольные точки сохраняются перед каждой новой попыткой. При отсутствии надёжного checkpoint ведущий не делает вид, что предыдущая стадия согласована.

## Implementation Units

### P0 — Feasibility начальных навыков и документная среда

**Covers:** R5, R8–R9; KTD2–KTD7. **Зависимости:** ядро U1–U7; требуемая read-only среда.
**Files:** server/execution/preparation/skills/; scripts/preparation_binding_probe.mjs (новый).

До обещания конкретных bindings реализовать document workspace/файловую проекцию и проверить реальные маршруты установленных навыков: интерактивные вопросы, intent/spec approvals, записи/правки документов, Git commit, обязательные внутренние handoffs и чтение файлов reviewers. Регистрация binding содержит доказанный route, требования инструментов, разрешённые переопределения и результат probe. Unsupported route не рекламируется как доступный. Проверить хотя бы один полный профиль до подключения пользовательского start_preparation; при невозможности показать конкретный блокер/альтернативный профиль без изменения upstream или имитации шагов.
**Сценарии:** сложная задача проходит поддержанный исходный workflow и отдаёт план; bounded задача не запускает реализацию и либо проходит доказанный профиль, либо отклоняет incompatible binding; private spec commit/readable CE doc-review действительно выполняются; исходники плагинов и целевой проект остаются без правок.

### P1 — Подготовка карточки, память и переходы

**Covers:** R1–R7, R10–R11; KTD1, KTD6, KTD8. **Зависимости:** ядро U1–U7.
**Files:** server/execution/preparation/ и API state-сервера; scripts/test_preparation_state.mjs (новый).

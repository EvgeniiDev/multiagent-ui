# Общее ядро запусков и три режима агентов

Дата согласования: 2026-09-30.
Уточнение от 2026-09-30: ядро использует существующие адаптеры porch и отдельные worktree; контейнеры участников и строгий контроль файлов перенесены к групповым режимам.
Статус: согласованный обзор поставок. Первая поставка детализирована в [техническом плане ядра](agent-core-implementation-plan.md). Результаты разработки фиксируются отдельно: [отчёт U1](../reports/agent-core-u1-runtime-inventory.md).

Дальнейшие направления: [agent-roadmap.md](agent-roadmap.md).
Источники: [Fusion](../research/4shygray/fusion-opus-gpt-obedinenie.md), [Swarm](../research/4shygray/swarm-roy-agentov.md), [Workflow](../research/4shygray/workflow-600-chasov.md), [полный цикл](../research/4shygray/vaybkoding-s-nulya-17-minut.md).

## 1. Результат и границы

Порядок поставок: **общее ядро с одним агентом → Fusion → оркестратор → Swarm**. Первая версия поддерживает **Devin, Codex и Pi**.

Работа начинается из карточки канбан-доски. Пользователь прикрепляет подготовленные требования и план, принимает их версии, выбирает сохранённый состав и запускает выполнение. Результат — проверенная ветка задачи и отчёт для приёмки. Слияние и публикация выполняются отдельно.

**Подготовка идеи — отдельная будущая фича:** извлечение намерения → функциональные требования → дизайн → план разработки. Сейчас создаём интерфейс передачи документов и согласований, которым впоследствии воспользуются Grill Me, Superpowers и Compound Engineering.

Режим относится к отдельному запуску, а не ко всей карточке. Несколько запусков могут последовательно готовить документы и реализовывать задачу. Реализация не начинается до принятия требований и плана. Изменение требований во время работы вызывает остановку и повторное согласование.

## 2. Первая поставка: управляемый запуск одного агента

### Карточка и входные документы

- Сохранить колонки `backlog → spec → plan → dev → reviewtest → done`. Добавить документы задачи, историю запусков, рабочую ветку и состояния ожидания согласования и приёмки.
- Документ имеет тип — требования, дизайн, план или результат — и неизменяемую версию. В карточку можно загрузить Markdown или выбрать файл проекта; при запуске сохраняется снимок содержимого.
- Для реализации обязательны принятые требования с критериями готовности и принятый план. Дизайн прикладывается при наличии.
- Изменение требований аннулирует согласование плана. Запуск фиксирует версии документов, настройки состава и исходный коммит.
- Связанный чат использовать для вопросов, комментариев и замечаний. Вопрос о статусе не меняет требования; изменение требований — отдельное явное действие.
- Автоматическое интервью и генерация требований в первую поставку не входят.

### Серверное управление

- Расширить существующие state-сервер и `server/acp-runner.mjs`. Сервер хранит состояние; раннер управляет процессами и переходами. Работа продолжается после закрытия браузера.
- Выделить планировщик участников, который запускает независимые попытки параллельно в пределах лимитов. Не ожидать завершения одного участника внутри общего прохода очереди.
- Ввести сущности запуска, участника, попытки, артефакта, согласования и события.
- Один управляющий процесс владеет claim карточки. Участники принадлежат запуску; старый диспетчер по `stageRoles` пропускает карточки нового механизма.
- Переиспользовать существующие адаптеры Devin, Codex и Pi из `porch`: Devin через ACP, Codex через app-server, Pi через RPC. Подключить запуск, события, результат и отмену к ядру acp-ui; дописывать только отсутствующие возможности. Не предполагать универсальную поддержку `--prompt-file`.
- Добавить серверные команды запуска, остановки, согласования и продолжения. Команда имеет уникальный идентификатор и ожидаемую версию состояния: повторная отправка не создаёт второй запуск.
- Использовать существующее серверное хранение с проверкой версий; локальный кеш браузера не является источником истины для команд выполнения.

### Рабочие деревья и среда запуска

- Реализация выполняется в отдельной ветке и worktree задачи от выбранного коммита. Агент запускается с `cwd` этого worktree и напрямую изменяет его файлы.
- В первой поставке агенты запускаются через porch обычными дочерними процессами в существующей среде раннера. Отдельные worker-контейнеры и серверный механизм подачи правок в ядро не входят.
- Сервисы acp-ui, включая раннер, продолжают работать через Docker Compose согласно AGENTS.md. Упрощение касается контейнеров отдельных участников, а не способа запуска стека.
- Worktree разделяет изменения задач, но не запрещает агенту доступ к другим каталогам. Не заявлять техническую защиту исходного проекта или запрет записи за пределами worktree. В установленном porch Devin использует bypass, Codex — danger-full-access; эти настройки нужно учитывать при подключении.
- Отделить запуск среды от протокола CLI: интерфейс запуска принимает рабочий каталог, окружение и расположение артефактов; возвращает идентификатор выполнения и операции наблюдения и остановки. В v1 его реализует процесс в среде раннера, позднее — контейнер.
- Хранить идентичность среды отдельно от CLI-сессии; PID и пути не должны становиться частью публичного контракта карточки. При восстановлении проверять принадлежность процесса и время его старта, а не только совпадение PID.
- Проверить авторизацию, доступность CLI и зависимостей проекта, события, результат и отмену для каждого адаптера porch в среде раннера.
- Перед Fusion добавить техническое ограничение записи и доступа к материалам. Перед Swarm добавить проверяемые права на файлы и механизм применения правок. Выбор конкретной песочницы или контейнерного backend уточнить перед соответствующей поставкой.

### Завершение, остановка и восстановление

- Код завершения CLI фиксирует исход попытки. Готовность определяется артефактами, критериями, проверками и ревью.
- Сохранить существующий цикл ревью и checker-гейт. Команды проверок берутся из принятого плана; отсутствие способа проверки требует уточнения.
- В первой поставке проверки выполняются обычными процессами в отдельной временной копии текущего результата; изменения от тестов не попадают в ветку задачи. Копия не является песочницей и не ограничивает доступ тестовых команд к остальной среде.
- «Изменить требования» прекращает выдачу работы, останавливает активные попытки и сохраняет правки. Продолжение создаёт новый запуск после повторного согласования.
- После перезапуска раннер сверяет попытки с состоянием porch и идентичностью принадлежащих им процессов. Живые продолжает наблюдать, если backend поддерживает подключение; иначе показывает необходимость восстановления. Потерянные помечает прерванными и не запускает дубликаты живых процессов.
- Повторная попытка получает результаты и незакрытые критерии. Лимиты попыток наследуются из настроек ролей.

**Приёмка:** готовую задачу можно запустить из карточки, остановить, продолжить и довести до проверенной ветки каждым из трёх CLI.

## 3. Групповые режимы

### Вторая поставка — Fusion

- Запускать 2–10 независимых панелистов с одинаковыми входами и одной версией проекта. Требовать минимум две разные явно настроенные модели.
- Панелисты имеют доступ на чтение проекта и собственных материалов. Ответы других участников и возможность применять правки им недоступны.
- Техническую изоляцию добавить до выпуска Fusion: запрет правок проекта и чтения чужих материалов, включая ответы панели для интегратора, должен действовать и для shell-команд. Промпты и расположение файлов в разных каталогах не обеспечивают этот запрет. Проверить адаптеры porch с выбранной средой выполнения.
- Контракт ответа: предложение, обоснование, затрагиваемые файлы, недостатки и исключённые действия. Веб-поиск включать через инструменты адаптера; поддержку проверять до запуска.
- После всех корректных ответов запускать судью. Он проверяет совпадения, противоречия, пропуски, уникальные идеи и слепые зоны; формирует наряд с критериями.
- Для документной задачи наряд является итогом. Для реализации его получает интегратор с доступом к проекту, но без доступа к ответам панели.
- Если наряд меняет требования или план, остановиться для согласования. Неуспешного панелиста повторить в пределах лимита; после исчерпания запросить решение пользователя.
- Интегратор отчитывается по критериям и явно указывает вынужденные отступления из-за фактического состояния кода.

### Третья поставка — оркестратор

- Оркестратор получает принятый план и создаёт подзадачи с зависимостями, результатами и критериями проверки.
- Каждый воркер работает в отдельной ветке и worktree. Независимые подзадачи запускаются параллельно; зависимые получают принятые результаты предшественников.
- Оркестратор принимает результат или возвращает конкретные замечания. Число циклов ограничивается настройками состава.
- Отдельный интегратор собирает принятые изменения в ветке задачи и разрешает конфликты. Затем выполняются общие проверки и ревью.
- Подзадачи показываются внутри карточки. Управляющая роль не реализует их сама; создание отдельной карточки для каждого воркера в v1 не требуется.

### Четвёртая поставка — Swarm

- Равноправные участники получают общую цель и читают один worktree задачи. Сервер обеспечивает протокол, модельного руководителя нет.
- Координация проходит без правок: участники объявляют свою часть работы, файлы, контракты и риски.
- Сервер фиксирует владение файлами и отклоняет пересекающиеся заявки. Права на изменение выдаются после согласованной координации.
- К поставке Swarm реализовать серверный механизм применения правок и ограниченную среду участников. Рабочее дерево доступно им для чтения; изменения подаются через команду `acp-run` с полномочиями участника. Это расширение ядра, а не часть первой поставки.
- Механизм проверяет владение файлами, исходную версию, допустимые пути и симлинки; создание, удаление и переименование проверяются также. Чужой файл нельзя изменить инструментом редактирования или shell-командой; writable mounts не должны открывать обход к проекту.
- Поддержать адресные сообщения, сообщения всем, предложения и обязательные решения. Решение становится обязательным после подтверждения затронутыми участниками; передача файла требует согласия владельца.
- Работу выполнять ограниченными ходами: между ходами участник получает накопленные сообщения, решения и сведения о чужих правках. Доставку внутрь занятого CLI в v1 не требовать.
- После реализации провести до трёх раундов догона и общие проверки. Неразрешённые конфликты переходят пользователю; тишина и отсутствие содержательного ответа не считаются согласием.
- Разрешить общий каталог только участникам одного запуска; защита от посторонних запусков сохраняется.
- Адаптер допускается к Swarm только после проверки технического запрета чужих правок.

## 4. Интерфейсы и пользовательский контроль

- Добавить типы `Run`, `Participant`, `Attempt`, `DocumentVersion`, `Approval`, `RunEvent`. Состояние задачи принадлежит карточке; текущий запуск и история входят в её представление. Запуски и попытки имеют собственные записи для истории. Сервер управляет переходами выполнения и защищает их от перезаписи старой копией доски из браузера.
- API первой поставки предоставляет составы, запуски, события с курсором, документы и команды жизненного цикла. Операции сообщений, владения файлами и применения изменений добавляются с соответствующими групповыми режимами.
- В ядре полномочия ограничивают операции API; они не ограничивают прямой доступ CLI к файловой системе. Технические ограничения материалов и правок Fusion и Swarm обеспечиваются средой выполнения и сервером при поставке этих режимов.
- В настройках сохраняются составы: роли, CLI, модели, ссылки на промпты, лимиты и команды проверок. Изменение состава не меняет созданные запуски.
- Промпты остаются файлами проекта. Модели указываются явно; автоматический выбор по цене или сложности отложен.
- В карточке показывать этап, участников, ожидания пользователя, результаты, проверки и ветку. Логи открывать по участнику.
- Расширить Workflow новыми запусками, сохранив чтение внешних прогонов `porch`.
- Проверять CLI, модель и возможности до запуска. Несовместимый состав не стартует; интерфейс показывает причину.

## 5. Проверки и внедрение

Каждая поставка проходит контрактные проверки на имитаторах CLI и реальные пробные задачи для Devin, Codex и Pi.

Обязательные сценарии:

- Двойной запуск, две вкладки, устаревшее согласование, недоступный сервер.
- Закрытие браузера, перезапуск раннера, зависание, отмена и исчерпание повторов.
- Ядро: корректные worktree и cwd, разделение изменений задач, проверки во временной копии, наблюдение и отмена через porch. Технический запрет доступа за пределами worktree не является критерием первой поставки.
- Fusion: независимость ответов, изоляция материалов интегратора, запрет записи панелистов и обхода ограничений через shell.
- Оркестратор: параллельность, зависимости, отклонение результата и конфликт интеграции.
- Swarm: запрет ранних и чужих правок, проверка исходной версии файла, владение файлами, доставка решений и ограничение раундов; попытки обойти контроль через shell и симлинки отклоняются.
- Регрессии карточек, claims, ревью и внешних Workflow-прогонов.
- ACP-инварианты: replay только своей сессии и независимость request-id разных сокетов.

Новые функции включаются только для явно переведённых на них карточек. Старые карточки и прогоны продолжают работать по прежнему пути.

Frontend собирается на хосте через `npm run build:web`; сервисы запускаются через Docker Compose. Порты сохраняются, Tauri-ветки не меняются. Изменения bridge вносятся в `deploy/acp-ws-bridge.mjs`.

Начальные составы: два панелиста или воркера; догон Swarm — три раунда. Первая версия работает с Git-проектами. Автоматическое слияние и публикация не входят в выполнение.

## 6. Перед реализацией

Для ядра использовать [технический план первой поставки](agent-core-implementation-plan.md): U1 проверяет porch в Compose-раннере, далее серверное состояние, worktree, отмена, восстановление, проверки и интерфейс. На старте следующих поставок сверять обзор с текущим кодом и уточнять интерфейсы и задачи. Для Fusion и Swarm отдельно выбрать и проверить среду, обеспечивающую необходимые ограничения; для Swarm реализовать механизм передачи правок.

Добавление контейнеров должно сохранять контракты карточек, запусков и событий через отдельный интерфейс среды выполнения. Это сокращает объём переделок, но не делает миграцию бесплатной: нужно проработать авторизацию CLI, зависимости, пути и тома, права файлов, отмену и восстановление. Контейнеры и гарантии контроля файлов пока не являются проверенными возможностями системы.

Полный процесс подготовки идеи и Swarm для совместного написания требований описываются отдельными будущими планами.

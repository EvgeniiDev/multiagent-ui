# Третья поставка: оркестратор

Решения согласованы: 2026-09-30. План сохранён: 2026-10-01.
Основание: [общий план](agent-execution-plan.md), [Workflow](../research/4shygray/workflow-600-chasov.md).

## Основа агентов: настроенные профили Pi

Согласовано 2026-10-01: постоянная архитектура — Pi как одна базовая среда агента и отдельные конфигурации ролей. Подготовка идеи, разработка, панелист, судья, интегратор и проверяющие роли запускают подходящий Pi-профиль с заранее установленными навыками/расширениями/инструментами. Поддержка этих фич сразу во множестве разных CLI не требуется. Разные профили — конфигурации одного harness, а не обязательное множество продуктов. Модели/provider/effort задаются явно и могут различаться; минимум двух разных моделей Fusion сохраняется.

AgentProfile содержит profileId/version, закреплённую версию Pi, provider/model/effort, skills и их версии, extensions/tools, системные инструкции, права и лимиты. Начальная проверенная версия Pi — установленная 0.85.1; профиль сохраняет её и digest ресурсов до запуска. Пакеты/ресурсы готовятся заранее, не устанавливаются из пользовательского prompt во время задачи. Профиль и навыки заменяются настройками; универсальный перевод workflow во все CLI не входит в работу.

Использовать отдельный PI_CODING_AGENT_DIR и HOME/каталог сессий для каждого participant attempt; неизменяемый шаблон профиля общий, writable session state отдельный. Pi поддерживает явные --skill/--extension, отключение автоматического discovery и --tools allowlist. Проектные extensions/settings по умолчанию не доверяются; не загружать их молча поверх выбранного профиля. Проверить, что вызов через porch сохраняет нужные profile flags/env; если wrapper мешает, добавить минимальную поддержку Pi-профиля вместо трёх универсальных адаптеров. Профиль задаёт инструменты, но реальные файловые/сетевые ограничения по-прежнему обеспечивает среда.

Интерактивность подготовки — Pi RPC и собственное расширение ACP UI: вопросы, документы, skill gates и пользовательские ответы через поддержанные RPC/extension-UI события. Плагинные исходники не патчить; нужны инструменты и их семантика в расширении Pi. Совместимость каждого нужного workflow проверяется реальным probe; перенос текста SKILL.md сам по себе не доказательство. Базовый процесс, роли и согласования принадлежат ACP UI; не строить отдельный universal SkillRunner для произвольных CLI.

Эта поправка действует для четырёх новых планов. Текущую реализацию ядра в другом чате не переписывать: её существующий process-runtime и legacy CLI остаются совместимыми, выбранные будущие роли используют Pi profiles. Реальные проверки новых режимов выполняются на участвующих профилях Pi, а не требуют запуска Devin/Codex.

## Goal Capsule

Выполнить принятый план параллельными воркерами, принять их результаты по критериям и собрать проверенную ветку задачи. Начинать после ядра U1–U7 и [Fusion F1–F4](agent-fusion-implementation-plan.md). Контейнерный backend и управление материалами переиспользуются; Fusion-панель не является обязательным этапом каждого запуска оркестратора.

## Product Contract

### Summary и Problem Frame

Последовательный исполнитель не использует независимость частей задачи. Несогласованные параллельные ветки дают результаты, которые не проходят проверку вместе. Оркестратор обеспечивает зависимости и приёмку, интегратор — сборку.

### Requirements

- **R1 — принятые входы.** Запуск из карточки фиксирует версии требований/плана, baseCommit, состав и лимиты. Управляющая роль не реализует код сама.
- **R2 — декомпозиция.** Автоматически создавать подзадачи с результатом, критериями проверки, зависимостями, границами изменений и назначенным воркером. Обычная декомпозиция не требует согласования пользователя. Изменение принятого плана или требований требует согласования.
- **R3 — параллельность и изоляция.** Независимые подзадачи выполняются параллельно; каждому — отдельная ветка/worktree и доступ только к своим материалам. Зависимая стартует после принятия всех предшественников на снимке с их собранными изменениями.
- **R4 — проверка.** Оркестратор проверяет критерии и доказательства; принимает результат или возвращает конкретные замечания. Exit=0 не означает приёмку. Принятый результат фиксирует commit/hash и неизменяемый отчёт.
- **R5 — частичный сбой.** После исчерпания попыток подзадачи её зависимости ждут решения пользователя; независимые задачи продолжаются. Принятые результаты сохраняются. После повтора изменённого результата зависимые результаты, основанные на старой версии, инвалидируются и проверяются/выполняются заново.
- **R6 — интеграция.** Отдельный интегратор собирает принятые результаты в ветке задачи в порядке зависимостей. Конфликты разрешает в рамках плана; изменение поведения выносит пользователю. После сборки — общие проверки, reviewer/checker ядра и приёмка снимка.
- **R7 — исправления.** Замечания адресуются воркеру или интегратору. Изменение результата требует повторной проверки соответствующей подзадачи и собранного результата. Исчерпанные циклы блокируют готовность.
- **R8 — управление.** Подзадачи показываются внутри карточки, без отдельной карточки на воркера в v1. Stop останавливает все попытки запуска и запрещает новые. Рестарт восстанавливает наблюдение и не создаёт дубликаты.

### Key Decisions

- **KD1 — автоматическая декомпозиция** (session-settled: user-directed — вместо обязательного подтверждения подзадач). Governs R2.
- **KD2 — продолжать независимую работу** (session-settled: user-directed — вместо остановки всех при сбое воркера). Governs R5.
- **KD3 — интегратор разрешает конфликты в рамках плана** (session-settled: user-directed — вместо запроса на каждый конфликт). Governs R6.

### Scope Boundaries

Оркестратор работает с готовым принятым планом; интервью, автоподбор моделей, дополнительные канбан-карточки и автоматическое слияние в основную ветку не входят.

## Planning Contract

### Key Technical Decisions

- **KTD1 — граф и scheduler.** Добавить Run.mode=orchestrator, фазы decompose/work/integrate и гейты ядра; Subtask с dependency IDs, входным снимком, участником, attempts, статусом, критериями и принятой версией результата. Валидировать уникальные ID, отсутствие циклов/неизвестных зависимостей и наличие критериев. Scheduler запускает готовые узлы с глобальными/ролевыми лимитами и durable попытками.
- **KTD2 — передача кода.** Перед проверкой подзадачи доверенный контроллер создаёт immutable resultCommit из полного снимка private repository, включая незакоммиченные tracked/untracked изменения и удаления. Доказательства относятся к этому commit, дальнейшие изменения не входят в принятый результат. Каждый принятый результат — diff между inputCommit и resultCommit; использовать только собственный diff, без повторного применения унаследованных изменений. Временную базу зависимого воркера строить топологически из уникального транзитивного набора предшественников. Алмаз графа не должен применить общий предшественник дважды. Снимок зависимостей сохраняется с hashes и отчётами.
- **KTD3 — конфликт базы.** Если сборка предшественников конфликтует, зависимый воркер не стартует. Интегратор подготавливает проверенную базу в рамках плана; её commit фиксируется как новый inputCommit. Разрешение хранить отдельным immutable IntegrationArtifact: входные resultCommit, порядок сборки, дерево до разрешения и результирующее дерево/commit с resolution delta. Resolution канонично для ключа точных входных resultCommit и стабильного топологического порядка сборки: все потребители одинаковой базы переиспользуют один artifact, независимо от параллельной подготовки. При объединении пересекающихся artifacts проверить их совместимость; несовместимость требует нового совместного resolution и инвалидации использовавших прежние версии потребителей. В происхождении dependency snapshot сохранять artifact ID. Финальная сборка обязана воспроизводить этот принятый artifact, не разрешать тот же конфликт заново иначе. Изменение artifact инвалидирует использовавших его потомков так же, как изменение результата воркера. Никакого неявного выбора одной из конфликтующих версий сервером.
- **KTD4 — результат и исправления.** Воркер получает принятую задачу, scoped workspace и замечания; оркестратор read-only. Интеграция выполняется отдельным writable participant. Изменение принятого результата ревизует граф: потомки получают stale-input, активные попытки потомков останавливаются до пересборки; несвязанные узлы продолжаются. Каждая попытка, проверка и финальная интеграция фиксирует поколение своих входов и точный dependency snapshot; сервер публикует accepted/verdict/готовность только при совпадении с актуальными входами узла/сборки. Позднее завершение инвалидированной попытки сохраняется в истории как stale, не оживляет узел и не открывает потомков/приёмку. Несвязанные обновления графа не инвалидируют актуальные входы независимого узла.
- **KTD5 — команды и отображение.** retry_subtask и resolve_subtask_issue расширяют команды карточки с commandId/revision. Вопрос по узлу хранится отдельно от Run.status: пока независимая работа выполняется, run active с pending action; blocked когда нет исполнимой работы. accept_result доступен только после общих гейтов.

### Assumptions и Defaults

Два воркера по умолчанию; две попытки на роль и до трёх циклов исправления, настраиваются до старта. Повтор не скрывает исчерпание: пользователь явно разрешает новый лимит/попытку. Роли и модели заданы явно. Backend, credentials, сеть и изоляция наследуются из Fusion F1.

## Implementation Units

### O1 — Декомпозиция и граф

**Covers:** R1, R2, R8; KTD1. **Зависимости:** ядро и Fusion.
**Files:** server/execution/orchestrator/, prompts/execution/orchestrator/; scripts/test_orchestrator_graph.mjs (новый).

Добавить контракт подзадачи, read-only роль декомпозиции, серверную валидацию и события графа.
**Сценарии:** обычное разбиение запускается без вопроса; изменение плана ожидает согласования; циклы, неизвестные зависимости, пустые критерии и повтор ID отклоняются; повтор команд не создаёт второй граф.

### O2 — Workspace и зависимые результаты

**Covers:** R3, R5, R8; KTD1–KTD4. **Зависимости:** O1.
**Files:** server/execution/orchestrator/ и workspace-модули ядра; scripts/test_orchestrator_workspaces.mjs (новый).

Контроллер владеет каноническими ветками/worktree. Каждому worker выдавать приватный автономный Git-репозиторий подготовленной базы, без alternates, hardlinks и ссылок на общий git-dir; собственный рабочий каталог rw. Импорт/экспорт snapshots выполняет контроллер. Запускать готовые узлы, готовить dependency snapshots с versioned reports и IntegrationArtifact. Материалы подаются через профили среды; Git работает внутри private repository, без доступа к refs/объектам чужих активных задач.
**Сценарии:** два независимых воркера одновременно; лимит concurrency соблюдается; цепочка и алмаз; конфликт базы до старта; git status/commit работает без общего git-dir, чужие refs недоступны; два конфликтующих родителя и два параллельных зависимых узла используют один канонический resolution artifact и тот же вариант при окончательной сборке; пересекающиеся artifacts проверяются на совместимость; независимые продолжаются при сбое; замена результата делает потомков stale; рестарт scheduler не дублирует воркера.

### O3 — Приёмка, исправления и сборка

**Covers:** R4–R7; KTD2–KTD5. **Зависимости:** O2.
**Files:** server/execution/orchestrator/, проверяющие модули ядра; scripts/test_orchestrator_integration.mjs (новый).

Сохранять immutable accepted snapshots, критерии, команды и доказательства. Отдельный интегратор собирает собственные diffs принятых результатов и сохранённые IntegrationArtifact с их provenance; ошибки общего теста возвращаются ответственным ролям. Не переносить доказательства на изменённый hash.
**Сценарии:** ложное DONE отклоняется; незакоммиченное изменение, новый файл и удаление попадают в resultCommit до проверки и передаются потомкам/сборке; изменение resolution artifact инвалидирует зависимый результат; поздний completion во время выполнения/проверки/финальной сборки не возвращает stale результат в accepted; конкретный возврат замечаний; конфликт в рамках плана разрешается; изменение поведения требует вопроса; полный результат не готов при прошедших только локальных тестах; исправление и повторные общие проверки; limit exhaustion виден.

### O4 — UI и выпуск

**Covers:** R1–R8. **Зависимости:** O3.
**Files:** карточка, managed Workflow и stores; scripts/e2e_orchestrator.py (новый).

Показать граф, попытки, принятые hashes, причины ожидания, открытые вопросы и интеграцию. Stop и continue используют жизненный цикл ядра.
**Сценарии:** две вкладки/409; retry узла; недоступный сервер; stop нескольких воркеров; восстановление после закрытия браузера; legacy и внешний porch reader.

## Verification Contract

Node-тесты O1–O3 с fake runtime и временными Git-репозиториями; Compose-backed прогон двух независимых задач, зависимого узла и конфликтной сборки. Реальные короткие роли через выбранные Pi-профили. Browser-сценарии O4; npm run build:web на хосте. Регрессии ядра, claims, review и ACP-инвариантов.

## Definition of Done

O1–O4 и R1–R8 подтверждены доказательствами. Зависимости передают код и отчёты правильной версии; частичный сбой сохраняет несвязанные результаты; полная ветка проходит гейты и приёмку. Удалены экспериментальные пути, задокументированы диагностика и восстановление. Merge/push остаются отдельными действиями.

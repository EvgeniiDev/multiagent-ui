# Pi session image cleanup — design specification

**Status:** Approved for implementation by GPT-6.1-Sol (`medium`) after v5 blockers were resolved
**Scope:** Current Pi session only. This is a design and review gate; no implementation, adapter change, or deployment is included here.

## Problem and goal

Long Pi session histories can contain many image blocks. Hiding the panel's thumbnails is insufficient because Pi owns the persisted conversation and may continue sending those image blocks to the model. Add a manual action that removes image content from the active Pi session while retaining its text conversation on disk.

The inspected session JSONL had 30 `type: "image"` blocks with about 8.81 million encoded data characters. This confirms the stored image count and size for that session only. It does **not** establish a provider image-count limit and does **not** establish that these images caused any observed HTTP 400 response.

## User-facing behavior

- Show **Clear images** only for an open Pi session. It is disabled while that session is loading or has a request in flight.
- Clicking opens a confirmation that states the operation affects only this Pi session, the active history will lose its images, and the backup will retain the originals.
- On confirmation, the operation does not invoke a model, does not add a user-visible transcript message, and must not be metered as a model turn (see Integration boundary).
- On success, say that image blocks were removed from this saved Pi session, show the count and private backup path, and note that currently connected compatible clients were cleared; offline clients are reconciled only after reconnecting with a generation-aware build (and may retain local bytes while unreachable); incompatible builds must update and are not claimed physically erased. Do not imply unreachable browser-local bytes were physically erased. Success requires every criterion in Operation sequence. Otherwise report explicit non-success with final state and backup location.
- Success copy must not promise that reasoning text or full tool inputs remain visible in the panel: disk preservation and UI replay are verified separately (see Persisted JSONL vs UI replay). Suggested wording: "Removed N image blocks from this session's stored history (backup: <path>). Text history preserved on disk; panel shows what Pi replays."
- If there are no images, report that and make no history change: no backup, no rewrite, no child close, no cache mutation.

## Concurrency gate (mandatory design)

Confirmed baseline (must not be re-assumed away):

- `deploy/acp-ws-bridge.mjs:803-814`: several sockets forward requests; `sessionOwner` is the last requester, not a lock.
- `deploy/patch-pi-acp-multisession.mjs:45-60`: coalesces identical concurrent loads; does **not** serialize prompt vs load.
- Therefore no existing bridge/patch mechanism serializes prompt vs load vs cleanup, and `sessionOwner` must not be treated as mutual exclusion.

Required gate design:

**Authoritative generation and cache transaction.** The acp-state-server is the sole durable authority for the attachment generation keyed by the UI's exact `attachmentScope = agentName::sessionId`; the Pi bridge gate remains keyed by ACP `sessionId`. Browser localStorage, Tauri plugin-store, Pi adapter-local flags, and a generic `attachments.json` revision are not authoritative.

- Add idempotent state-service protocol v1 operations `POST /api/pi-session-images/read`, `/begin`, `/maintenance-snapshot`, `/commit`, and `/abort`, keyed by exact `{agentName, sessionId, attachmentScope, transactionId}`, where `attachmentScope` must equal `${agentName}::${sessionId}`. `read` reports generation and transaction state for that scope. Every cross-file update to the generation ledger and `attachments.json` uses a durable intent/recovery record in `STATE_DIR`, serialized on the existing state-service write queue; State-service startup repairs only incomplete local file writes from that intent; it never chooses the cross-system Pi transaction outcome without the adapter journal, and retains `pending` until explicit adapter commit/abort. Bridge-to-state-service begin/commit/abort require server authentication; browsers never receive that credential. `begin` returns a short-lived unguessable maintenance lease bound to transaction/scope/generation for filtered snapshot/purge only, never image bytes or session-gate bypass. Each transition is idempotent and fault-injection tested.
- `begin(expectedGeneration, transactionId, attachmentScope)` atomically increments that scope's generation and records a durable `pending` transaction with a snapshot of only that scope's attachment metadata. While pending, block **all ordinary reads/writes/hydration** for C, not just stale-generation operations; state-service writes to other scopes remain allowed. Preserve the snapshot and image bytes (no deletion yet). Only transaction-ID-scoped maintenance operations described below may inspect this snapshot. Duplicate begin for the same transaction is idempotent; mismatched expected generation conflicts.
- Generic `/api/state/attachments.json` writes are serialized with these operations. The state server preserves its generation high-water mark and target-scope tombstone: stale or unversioned writes cannot reintroduce C's old image metadata; while C is pending, writes may update other scopes but must preserve C's pending snapshot unchanged. No current-generation writes to C are accepted until commit/abort resolves.
- After the sanitized JSONL has replayed successfully and every connected compatible client has acknowledged target-only invalidation and tagged sanitized reload, `commit` removes only `kind: "image"` metadata for the target `attachmentScope`, preserves text/non-image attachments and all other scopes, and durably marks that transaction committed. `abort` is permitted only after the original JSONL is restored and verified; it advances generation again, restores only the saved C attachment record into the latest document (preserving concurrent changes to every other scope), and clears pending. No writes to C are accepted while pending, so this restoration cannot erase later text/non-image edits; state-service startup recovery must enforce the same write fence and apply only the target C record from its durable intent, never replace the whole document. Never decrement/reuse a generation. Lost responses are resolved by reading the exact transaction record.
- Each web/Tauri client tags attachment records and all reads/writes with the server generation. Before local-tail/attachment hydration or any retry/flush, it must read the authoritative generation. During `pending`, all ordinary attachment/history reads, writes, hydration, binding and caller-driven replay fail closed. Only the gate-owning adapter controller, authenticated server-to-state-service and bound to the exact transaction lease, may call `/maintenance-snapshot` to obtain an immutable snapshot filtered to non-image metadata plus exact image-only cache references for target-only purge; it never receives image bytes. While pending, the controller may issue one transaction-scoped maintenance replay using the exact `{transactionId,generation}`; clients accept only that tagged sanitized stream, render text/non-image metadata from the filtered projection, and bypass all image-cache lookup. These maintenance operations cannot call generic state reads/writes or perform a model turn. No external `session/load`, prompt, or caller can use either bypass. A stale localStorage mirror, Tauri plugin-store, or queued offline write cannot overwrite a newer generation.
- Connected compatible clients physically remove addressable image-only cache bytes for S and clear all target image references before acknowledgment. Keep target text metadata and any bytes still shared with text/other-session records. Offline clients may retain device-local bytes while unreachable; reconnect fencing prevents use and schedules deletion.

1. The lock/gate is owned by the Pi adapter (server side, where the Pi child lifecycle and JSONL path live), keyed by ACP `sessionId`, and shared across all sockets. A browser-side or per-socket flag is not sufficient.
2. All operations for that `sessionId` — `prompt`, `load` (including in-flight restore/replay), and cleanup — serialize through this gate. In-flight restore counts as busy.
3. While the gate is held by cleanup: reject new external prompts/loads/cleanups for that `sessionId` with a deterministic fail-fast busy error (no indefinite wait, no queueing or joining behind cleanup). Other session IDs remain available. Exactly one cleanup in flight per `sessionId`.
4. The internal reopen/replay step of the cleanup itself must be able to proceed under its own held lock without deadlock (e.g. re-entrant hold or explicit internal bypass scoped to the owning cleanup operation only). External requests must not be able to use this bypass.
5. Busy detection must be deterministic and testable: explicit adapter-owned states (e.g. prompt in flight, restore/replay in flight, cleanup in flight, queued turn present) — exact state names are an implementation detail, but the spec requires that "busy" is derived from adapter-owned state, never from UI disabled flags or `sessionOwner`.
6. **Implementation-plan deliverable — dedicated control method:** the plan must define the exact RPC shape and a dedicated Pi adapter control method intercepted before Pi's model-facing prompt operation; it must **not** reuse `session/prompt`. Runtime proof that it never reaches a model and never passes through/charges the bridge's ordinary-RPC `meterOutbound` is an implementation acceptance gate.
7. **Routing/lifecycle coverage:** the gate also covers adapter-triggered restore/spawn paths from set-model, set-mode, set-config, cancel, delete, close, and reconnect. The bridge must not change `sessionOwner` or route `session/update` to a rejected external request. Cleanup owns a logical session route independent of the initiating socket; internal replay goes to all live compatible subscribers. Keep the shared bridge alive during the operation; watchdog and socket-close paths must not orphan the transaction. An initiating client disconnect does not cancel after mutation begins; if no clients remain, finish durable recovery server-side and expose the recorded result on the next compatible reconnect.
8. **Exit proof:** `child.killed` is not exit proof. Retain the child record and await its exit event/PID absence before touching its JSONL or starting a replacement; ignore late callbacks from the old child by generation token.
9. **Client compatibility/admission:** v1 supports web and Tauri clients that implement generation invalidation. Before backup/mutation enumerate all clients bound to S. Every connected client must advertise support; if any is missing/unknown, refuse before backup or generation/file mutation. While S is gated, reject new/incompatible bindings before local-tail hydration; a compatible new binding joins the acknowledgment barrier. A disconnected client is offline and not physically purged until reconnect, but must check authoritative generation before any hydration/write. Unsaved composer attachments are outside the saved-history operation and must not be cleared.


## Operation sequence and safety transaction

`S` is the selected ACP Pi `sessionId`; `C` is its UI attachment scope `${agentName}::${sessionId}`. All cache/state operations target C, while Pi-file lookup, child lifecycle, and gate target S. Ordered steps for target S/C:

0. **Gate.** Acquire the per-session adapter gate for S. If busy (prompt/load/restore/cleanup in flight, queued turn present) or a second cleanup is in flight: refuse fail-fast with a busy error; touch nothing.
1. **Resolve.** Resolve S → exactly one session JSONL path via the adapter's existing mapping. Fail closed on unknown S, missing file, or ambiguous mapping (zero or more than one candidate): no backup, no mutation, no child action. The browser never supplies an arbitrary filesystem path.
2. **Parse fully.** Read and validate the entire JSONL before any mutation. Malformed/truncated JSONL: fail closed before mutation.
3. **Zero-image no-op.** If no `type: "image"` content blocks exist (including image blocks with missing/empty data, which count as image blocks when present): true no-op — no backup file, no rewrite, no child close, no cache mutation. Report "no images".
3a. **Read-only generation-service preflight.** After parsing and confirming images exist, verify the local acp-state-server advertises the versioned Pi-session image API. Its authoritative per-scope generation and idempotent transaction records are persisted under `STATE_DIR` and serialized on the existing state-service write queue; browser localStorage, a per-socket flag, or an attachment-document revision is NOT the authority. If unavailable/unsupported, refuse before backup or child close.
4. **Backup.** Create an exact byte-for-byte backup beside the session file before mutation, with a unique hidden/non-`.jsonl` name and mode `0600`; fsync the backup AND containing directory. Do not preserve the target's broader permissions on the backup. It intentionally retains original image data until the user deletes it.
5. **Sanitize in memory.** Only inspect the defined Pi message `content[]` arrays and replace each block whose `type` is exactly `image` with `{type:"text", text:"[Image removed manually]"}` in the same position. Do not recursively treat image-shaped objects inside tool args/results or unrelated metadata as image blocks. Preserve every other record, field, and byte range (text, reasoning, tool args/results, timestamps, IDs, metadata); preserve line endings/encoding. Count only replaced content blocks.
6. **Prepare + durable journal.** Write sanitized content to a same-directory exclusive temp file with mode `0600`, preserve required target metadata separately, and fsync it. Create a private journal recording session identity, original inode/digest/metadata, exact backup and temp paths, target generation and phase `prepared`; fsync the journal file AND parent directory. This durable journal must exist before any child close, generation CAS, or rename. Before each following phase, atomically update the journal through an exclusive same-directory temp, fsync the temp, rename it over the journal, then fsync the parent directory; keep the previous valid journal until the new phase is durable. Required phases: `prepared`, `child-closing`, `child-exited`, `advancing-generation`, `generation-pending`, `quiescing`, `quiesced`, `replacing`, `replaced`, `replaying`, `purging`, `commit-decided`, `committing`, `committed`, `aborting`, `aborted`, `recovery-required`. Journal/backup/temp names must not match session discovery. Fail on any durability error before close. Do not replace the target yet.

7. **Close only the target child and confirm exit.** Do this before replacing the active file. Do not spawn another child unless the old child’s exit event/PID absence is confirmed. If exit is not confirmed by the planned timeout, keep S gated; do not rename, reopen, or release prompts for S while the old child may still be alive. Other sessions remain available.
8. **Generation fence CAS.** After confirmed child exit, durably journal phase `advancing-generation`, then call the state service's idempotent `POST /api/pi-session-images/begin` with `{protocolVersion:1, agentName, sessionId, attachmentScope, transactionId, expectedGeneration}` (server validates the exact scope). On success it atomically increments S's authoritative generation, stores a durable `pending` transaction record and rejects all old-generation metadata/cache writes and hydration for S; it leaves image cache bytes and attachment metadata intact until the JSONL replacement is confirmed, so rollback can restore the original view. The operation is serialized with all generic `/api/state/attachments.json` writes. Those writes must preserve any newer generation/tombstone and reject/strip stale or unversioned S records; they may still update other sessions. A lost response is resolved by reading the transaction ID. Continue only if this transaction's `pending` generation is confirmed; otherwise remain gated and recover.
9. **Quiesce old-generation work BEFORE JSONL mutation.** Block new readers/writers and bindings for S; cancel/await active byte reads, runtime replay-merge buffers, in-memory AttachmentMeta references, local/shared tail reads/writes, KV snapshots, localStorage mirrors, Tauri plugin-store/cache work, timers, retry queues, and pending flushes. Clear currently rendered target image previews/derived attachment metadata and require acknowledgments from all connected compatible clients. Do not change textual history or composer attachments. If any old-generation task cannot be fenced/awaited, do not rename; restore/reopen original and rehydrate it under the advanced generation, or remain recovery-required.
10. **Recheck then atomic replace** the target JSONL with the prepared sanitized file. Durably journal phase `replacing` first. After child exit, generation fence, and quiescence, recheck inode/device, bytes, mode and owner against the original snapshot immediately before rename. On mismatch, preserve the current external file and enter race recovery; never overwrite it. A successful rename is the mutation boundary. If a subsequent durability/fsync step fails, inspect actual file state and recover; do not assume rename was undone.
11. **Replay, purge, and prepare to commit.** Using the gate-owning transaction ID, call `/maintenance-snapshot` and purge targeted image-cache bytes first while retaining the original JSONL backup and attachment snapshot for rollback. Pending state blocks ordinary reads/writes; use only the transaction-scoped non-image metadata projection. Then reopen S after confirmed prior-child exit and replay sanitized JSONL via a tagged internal maintenance update `{transactionId,generation}`; it may publish text and preserved non-image attachment metadata only, and must never consult any image cache. Suppress all model-turn/token estimate updates. Wait for acknowledgments from every connected compatible client (including any admitted during the operation). Then durably journal `commit-decided`; all rollback-capable work is complete, and the recovery policy is forward-only from this point. Do not call the state service `/commit` before this durable decision. If replay or pre-commit cache purge fails, request close-only for any replacement child and await its exit event/PID absence before touching JSONL; if exit is unknown, stay gated without restoring. Then atomically restore JSONL from the exact backup, verify the original hash, call `/abort`, rebuild connected caches from the original, reopen/replay original history under the new generation, and keep S gated until all parts are verified.
12. **Commit.** After `commit-decided`, call the idempotent `POST /api/pi-session-images/commit` with `{protocolVersion:1, agentName, sessionId, attachmentScope, transactionId, generation, sanitizedDigest}`; the state service removes only image metadata for `attachmentScope`, preserves text/non-image attachments and every other scope, and marks the transaction `committed`. Resolve lost responses by transaction-ID read-back. Do not report success or release the gate until both state service and file journal confirm committed state. If the service is unavailable after `commit-decided`, do not roll back; retain the sanitized file, backup, journal and gate in `commit-pending`, retry at startup/reconnect, and report non-success/pending to a still-connected caller. Once both durable records confirm commit, unlink/fsync the transaction journal; if cleanup fails, keep committed state, release only if verified, and report success with a cleanup-pending warning. On restart, reconcile the two transaction records by transaction ID and sanitized digest; never start a model prompt while they disagree.
13. **Success criteria (all required):** sanitized file on disk with zero active image content blocks; backup byte-identical to the original; previous target child exit confirmed; target child reopened from sanitized file; sanitized replay loaded for S without model-meter side effects; new authoritative generation rejects old writes; all connected compatible clients acknowledged target-only image-cache invalidation and sanitized reload; text/other-session data intact; no stale target thumbnails in those clients. State explicitly that offline devices may retain local bytes until they reconnect with a generation-aware build, which must fence and clear them before hydration; incompatible builds must update and are not claimed physically purged. Any unmet criterion is non-success with exact file/child/journal/generation/client states and backup path.

Failure semantics per step:

- **Detected external file race before rename:** do not overwrite or restore over the external writer. Leave the current path/content untouched, keep the original backup and transaction evidence, and enter recovery-required; report that external change explicitly. The supported writer boundary is one Pi ACP adapter per session; direct Pi CLI/other external writers are unsupported and detected where possible, not claimed to be lock-coordinated. A race is never a success.
- **Before the mutation boundary:** validation, resolve, backup, temp preparation, generation-CAS, or rename failure leaves the active path untouched by cleanup. If the child was already closed, reopen the observed file only after its previous exit is confirmed. If CAS advanced generation, reconcile clients and rehydrate the observed original before releasing the gate. Release only after file/child/runtime/generation state is coherent; otherwise retain recovery-required.
After the JSONL rename but before durable `commit-decided`, any error (including directory fsync, cache invalidation/purge, reopen/spawn, replay, hydration, or transcript publication) is non-success and enters rollback. Restore the exact backup only after confirming the prior child exit; then call state-service `/abort` against the verified original digest, rebuild cache metadata/bytes as needed, and replay original history under the newer (never decremented) generation. If restoration or client coherence cannot be verified, keep S gated. After durable `commit-decided`, rollback is forbidden: finish `/commit` forward under the gate; unavailable/ambiguous state-service confirmation is `commit-pending` and must never be reported as success.
- **After durable `committed`:** never roll back the sanitized history. If journal unlink or its directory fsync fails, retain the committed journal, report success with a cleanup-pending warning, keep the backup, and let startup finalize journal cleanup after digest/generation verification.
- **Gate release invariant:** release the gate only when the active file, child lifecycle, cache generation, and published UI state are known to be mutually consistent. Any unknown exit state, incomplete rollback, failed cache recovery, or failed hydration keeps S gated and refuses new prompts/loads until recovery. Retain the backup and report the exact recovery action. Never claim success.
- **Required recovery transitions:** errors before a durable `prepared` journal leave the original path untouched and require no backup restore. Recovery is determined by the durable adapter journal phase, not a generic `uncommitted` label: before `commit-decided`, confirm all relevant child exits, restore the original JSONL if replaced, verify its digest, call `/abort` if `/begin` succeeded, rebuild/replay original under the incremented generation and verify client coherence; if any child exit or external-file identity is unknown, preserve artifacts and remain gated without restoring. At and after durable `commit-decided`, rollback is forbidden: retry `/commit` forward until state service and journal agree on the sanitized digest. For `committed`, verify digest/generation and finalize journal cleanup. State-service startup repairs only its own incomplete local file-write intent; it must retain `pending` and must not infer the cross-system outcome without the adapter journal. On adapter restart, gate affected sessions before `session/list`, hydration, restore, or load; reconcile adapter journal with the state-service transaction by transaction ID and digest using the phase rules above, including lost `/commit` responses. Never accept model traffic while the outcome is ambiguous. After a detected external race, never overwrite external state. A timeout with a live/unknown child remains gated; resume only after confirmed exit. Closing the initiating tab does not stop server-side recovery. If file identity differs from both journaled original and sanitized digests, preserve it and require operator recovery. Failed recovery leaves S unavailable with all artifacts retained. Persist operation result by transaction ID for reconnect without rerunning cleanup.
- **Normative state outcomes:** (a) original + child alive before close: ordinary service unless cleanup gate held; (b) live/unknown child after exit timeout: gated, no rename/reopen/prompts/restoration until confirmed exit; (c) original + child exited + generation unchanged: reopen original and release only if healthy; (d) original + child exited + generation advanced before `commit-decided`: use the adapter journal to prove the transaction is pre-decision, abort that exact pending transaction, replay original under the next generation, and release only after client acknowledgment; (e) sanitized + no child after rename: gated; if journal is before `commit-decided`, rollback from backup only after confirmed child exit, then abort/replay original; if journal is at/after `commit-decided`, only forward-commit; (f) sanitized + replacement replay underway: gated; pre-decision failure requests close-only, waits for confirmed exit, restores backup, aborts and replays original under current generation; post-decision recovery keeps sanitized file and retries commit; (g) original restored + replacement replay underway: gated until original-history/current-generation replay and client acknowledgment; (h) external path/file mismatch: never overwrite, preserve artifacts and require operator recovery; (i) bridge restart with journal before `commit-decided`: gate S, confirm child exit, restore backup only if required, abort pending state-service transaction, replay original under current generation before accepting loads; with journal at/after `commit-decided`, retain sanitized file and only finish commit forward; state-service-only intents never decide this cross-system outcome; (j) committed journal: verify sanitized digest/generation and finalize cleanup; (k) committed journal unlink/fsync failure: remain committed, report success-with-warning, retry cleanup at startup. In every gated state no external prompt/load/delete/model/config/mode/cancel or new incompatible binding can mutate, hydrate, or reroute S.
- **State matrix required in the implementation plan:** expand these normative outcomes with exact file inode/digests, journal values, child PID/exit evidence, cache generation/client acknowledgments, backup/temp retention, error text, and permitted transition for each injected failure: timeout/live child, CAS failure, rename/fsync failure, partial purge, failed rollback hydration, adapter restart, socket disconnect, and post-commit journal-cleanup failure.
- **Cache rollback limitation:** once cache invalidation/purge runs, a file-level backup restore does not restore client-visible cache state. Recovery must explicitly restore/rebuild or invalidate/reload caches from the chosen file state; if that cannot be proven, keep S gated and report recovery-required. Acceptance covers partial purge and failed cache recovery.

## Filesystem guarantees

- **Resolution:** enumerate candidates for adapter-resolved S and verify exact session identity/uniqueness; do not trust a first-match fallback. Fail closed on ambiguity. The implementation plan must state the regular-file/symlink policy (default: refuse symlinks and non-regular files unless an alternative is justified and tested).
- **No collisions/overwrite:** backup and temp files use unique exclusive creation (e.g. exclusive-create with unique suffix; never fixed names, never silent overwrite of an existing backup).
- **Permissions:** backup and staging temp remain mode `0600`; immediately before rename, set the replacement's owner/mode to the original target's exact owner/mode or fail before rename. Never broaden backup permissions or silently change target ownership/mode.
- **Preservation:** newline- and encoding-preserving JSONL processing; every non-image record and field preserved (see Persisted JSONL vs UI replay for the disk/UI split).
- **Atomicity/durability:** same-directory temp file + atomic `rename`; fsync the backup, temp file, and containing directory, and verify this in tests. If the filesystem does not support these guarantees, fail closed before mutation; do not silently weaken to process-atomic-only.
- **Path policy:** refuse symlinked session files and symlinked parent directories; verify realpath remains beneath the adapter-owned session root and retain directory/file handles or equivalent identity checks through rename. Require a single adapter writer per target; direct Pi CLI/external writers are not coordinated by the gate.
- **Race check:** immediately before rename, compare path inode/device, bytes (cryptographic digest plus length), mode, and owner with the snapshot. If any differ, preserve the current external state, never restore the snapshot over it, and enter the specified external-race recovery path. This narrows but does not claim to prevent uncooperative external writers.

## Cache and replay (inventory, ordering, stale clients)

Confirmed baseline (must be handled, not assumed away):

- `src/lib/sessionRuntime.ts:560-581`: replay merge keys attachment records by attachmentScope + turn index and can return cached image previews/bytes — a stale image cache can resurrect thumbnails after a sanitized reload unless invalidated or filtered before replay consumption.
- Live message arrays and cloned `AttachmentMeta` values in each `sessionRuntime` (`src/lib/sessionRuntime.ts:125,560-581,648-687`), plus both `replayMerge.cached` and `.buffer` (`sessionRuntime.ts:215-220`), are independent owners; target generation checks must cover every render/publication boundary, not just stores.
- `ChatView.vue:184-195` and `src/lib/attachments.ts:153-211` can derive attachment placeholders from replayed text markers. For the cleaned session generation, preserve that source text literally but never rebuild image preview metadata/bytes from it. Do not clear unsaved composer attachments.
- `src/lib/attachmentHistory.ts` holds the in-memory attachment document indexed by `attachmentScope = ${agentName}::${sessionId}` (`sessionRuntime.ts:487-490`); `forgetSessionAttachments` deletes the entire scope record at `attachmentHistory.ts:295-300`, including non-image/text metadata, so it must **not** be used.
- Confirmed source-backed stores include `acp-ui:att-cache:*` (`src/lib/attachmentHistory.ts:143-170`), module-level attachment doc (`attachmentHistory.ts:57-69`), local tails (`src/lib/historyCache.ts:50-51,98,113-145`), shared tails (`src/lib/historySharedCache.ts:10-17,29-64`), replay publication/tail writes (`src/lib/sessionRuntime.ts:687,701-741`), KV snapshots and localStorage mirrors (`src/lib/host/storage.ts:59-79,158-169,222-238,293-350`), cached `webStores` (`host/storage.ts:570,604-610`), Tauri plugin KV store (`host/storage.ts:589-601`), Tauri AppCache image bytes (`attachmentHistory.ts:122-137,178-188`), conflict retries/queues, timers, async writes/flushes (`sessionRuntime.ts:1403-1409,1622-1631,1800-1802`), and backend attachment storage (`server/execution/state-service.mjs:717-755`). The current `RemoteKVStore` treats revision conflicts as last-write-wins and can force-put a stale whole document (`src/lib/host/storage.ts:302-327`); generation/tombstone enforcement must therefore live in the state-service write queue, not only in Vue/client code. The inventory covers all stores found in this inspected revision; add any newly discovered store before implementation.

Required behavior:

1. **Inventory gate:** implementation covers each confirmed store and runtime owner above, and the exact target attachment scope `agentName::sessionId`; generation-check reads and publications, invalidate/cancel old-generation timers, retries, async byte reads and writes before JSONL mutation. Any added store lacking proven target-only invalidation/filter forces fail-closed — never silent success.
2. **Target-only mutation:** addressably mutate only S's attachment record(s); preserve other sessions' records and all text/non-image metadata. No whole-doc stale overwrite that would clobber other sessions or resurrect S's images.
3. **Ordering:** CAS-fence and propagate the new generation, then stop/cancel/await old-generation readers/writers and clear rendered target images before JSONL mutation. After replacement, purge addressable caches, reopen, replay, publish and hydrate/write only the new generation. Tests observe the whole interval. Normal replay followed by purge is forbidden.
4. **Byte purge scope:** delete cached byte values only when image-only and unreferenced (no other record references the same bytes); never delete bytes still referenced by text/non-image records or other sessions.
5. **Stale/concurrent clients:** web and Tauri clients with generation-aware builds are supported; any connected unknown/legacy client blocks cleanup before mutation. Every compatible connected client acknowledges invalidation and sanitized reload before success. While gated, reject new/legacy bindings before local-tail hydration. Offline clients are outside immediate physical purge; on reconnect they read authoritative generation before hydration, clear old target caches, and reject old-generation writes. CAS conflict or unavailable service fails closed. Never report success while a connected client can write old images back.
6. **Backend failure:** if the cleanup backend (adapter/bridge path) fails during cache purge/hydration, the operation ends in explicit non-success/recovery state with the exact failed store, current file/child state, and backup location — never success with a stale cache.

## Persisted JSONL vs UI replay (must not conflate)

- **Disk (must preserve):** the sanitized JSONL retains all non-image records and fields, including reasoning content, tool call arguments, tool results, timestamps, IDs, and session metadata — byte/semantically preserved except for the image-block → marker substitution.
- **UI replay (known Pi 0.0.33 limitation):** installed `pi-acp/dist/index.js:1628-1636,2535-2544,2580-2602` normalizes replay to text blocks only; assistant thinking/non-text content is skipped and non-bash tool replay carries `rawInput: null`. The panel therefore cannot be expected to re-display reasoning or full tool inputs that Pi itself does not emit on replay.
- Consequence: acceptance verifies (a) disk preservation from the sanitized file + backup diff, and (b) UI behavior only against capabilities Pi actually emits. Never assert "reasoning/tool args visibly preserved in the panel" unless a preserving-replay path is implemented later. Either implement a preserving replay later as separate scope, or keep acceptance as disk-preservation plus replay-capability-limited UI checks. User-facing success copy must reflect this split (see User-facing behavior).

## Integration boundary

The capability is Pi-specific and must not be exposed as a generic ACP operation for other agents. The current Pi adapter is version-pinned (`pi-acp` 0.0.33) and patched by `deploy/patch-pi-acp-multisession.mjs`; any adapter change must preserve its existing multi-session behavior. A front-end-only cache deletion is explicitly not an implementation of this feature. The installed `pi-acp` 0.0.33 `restoreSession()` may dispose a `killed` child and spawn its replacement in the same call (the existing regression test at `scripts/test_pi_acp_multisession.mjs:93-104` asserts this). Therefore it is **not** a close-only primitive: never call it while the target JSONL is being replaced. The implementation plan must provide and prove a close-only/exit-wait operation that does not spawn; if unavailable or not verified on a disposable session, refuse the cleanup before mutation.

The adapter action must use the dedicated internal control path from the Concurrency gate section (never ordinary `sendPrompt`/`session/prompt`), so it is not shown as a user message. Both `meterOutbound` and inbound replay metering/token estimates/live-work evidence must be suppressed for maintenance and recovery replay; replay notifications otherwise look like ordinary model activity. Preserve the current session selection.

## Failure and concurrency cases

- Busy or queued selected session (prompt/load/restore/replay in flight): refuse without touching the session file, backup, child, or cache.
- External prompt/load/cleanup arriving during a held cleanup lock: refuse fail-fast; only the owning cleanup's internal reopen may proceed under its own lock.
- Rejected load from another socket cannot change `sessionOwner` or redirect internal `session/update`; cover set-model/mode/config, cancel, delete, close, reconnect, socket disconnect, bridge watchdog timeout and delayed old-child callbacks during cleanup/recovery.
- A second click/request while cleanup is in progress: fail-fast busy refusal; never queue/join implicitly or run two rewrites. Idempotent joining is out of scope unless a separate explicit contract is designed and tested.
- Cross-socket prompt/load/cleanup races and in-flight restore during cleanup: covered by the adapter-owned gate; `sessionOwner` and load-coalescing are not substitutes.
- Malformed/truncated JSONL, missing file, unknown/ambiguous `sessionId`, symlink/non-regular file (per policy): fail closed before mutation.
- Backup/temp/atomic-replace error, permission/owner-preservation failure, or read→replace race: keep the original active file and show an actionable error.
- Child exit timeout, failed spawn/reopen, replay failure, cache purge/hydration failure, or any incomplete rollback: exact-state error + backup location + safe retry; retain the backup and gate S until file, child exit, cache generation, and UI state are confirmed consistent.
- Other Pi sessions: their processes, histories, and cached transcripts must remain unchanged.
- Non-Pi agent: no cleanup action is shown and no Pi-specific request is sent.

## Verification and acceptance criteria

Fixture-only. No live user session is ever used. No paid model call is made for the cleanup path. Report unit/contract, protocol/gate, cache/replay, browser, and disposable live-runtime evidence separately.

### Unit/contract tests

- Fixture JSONL with multiple image blocks: image-only user messages, mixed text/image messages, image blocks with missing/empty data, reasoning records, assistant messages, tool calls/results (including args/results fields), and non-message session records.
- Verify only `type:image` blocks inside Pi message `content[]` become text-marker blocks; image-shaped objects in tool args/results remain unchanged. Verify all other records/fields are preserved and the backup is byte-for-byte identical.
- Verify zero-image input is a true no-op: no backup file created, no rewrite, no child action, no cache mutation.
- Verify malformed/truncated JSONL, missing file, unknown/ambiguous session ID, symlink/non-regular file, backup failure, atomic-write failure, permission/owner mismatch, inode/mode/owner/content race, and parent-path substitution do not report success; on detected external race, preserve the external file without overwriting it.
- Verify backup/temp/journal uniqueness (no collision/overwrite, never session-discovery candidates), private mode, preserved target mode/owner, newline/encoding preservation, and the stated fsync/durability policy. Exercise LF/CRLF, whitespace, escaped strings, trailing newline/no trailing newline, multiple image blocks in one line, and unsupported encoding/schema refusal with byte-level diffs.
- Verify disk preservation of reasoning/tool-args/tool-results fields from file diff (independent of what the UI panel shows).

### Protocol/gate tests

- Cross-socket prompt vs cleanup, load vs cleanup, and cleanup vs cleanup for the same `sessionId`: deterministic busy refusal; rejected load cannot change `sessionOwner`; exactly one rewrite.
- In-flight restore/replay vs cleanup: deterministic fail-fast busy refusal before mutation; never wait, join, or interleave a rewrite under an active replay. Replay-merge resurrection is covered by the cache-ordering test below.
- Busy/queued session refusal is deterministic and reproducible (adapter-owned state, not UI timing).
- Lifecycle methods (set-model, set-mode, set-config, cancel, delete, close, reconnect) are refused or safely serialized while S is gated; rejected requests cannot redirect replay notifications. Test watchdog/socket disconnect and late callbacks from a child whose exit has not yet been confirmed.
- Prove the maintenance path uses the dedicated control method: no model invocation, no user-visible message, no outbound or inbound replay metering/token-estimate/live-work change. Ordinary `session/prompt` reuse fails this test.
- Incompatible connected client and missing generation/CAS service refuse before backup/file mutation; every compatible connected client must acknowledge invalidation/reload. New bindings during the gate cannot hydrate local tails before generation validation.
- Child exit timeout while live, CAS failure/lost response (including read-back resolution), failed spawn/reopen, every journal/file/directory fsync boundary and crash-restart phase, post-rename failure, rollback failure, partial cache purge followed by failed recovery hydration, adapter restart with uncommitted/committed journal, and cache-backend failure each produce the specified exact-state result; S remains gated on unknown/inconsistent state.
- Update the existing `scripts/test_pi_acp_multisession.mjs` contract that currently expects replacement on `child.killed === true` with null exit codes: signal-sent while process is still alive must not permit replacement; verify replacement only after confirmed exit.

### Cache/replay tests

- After sanitized reload, no image preview/bytes for S return via replay merge, local/shared tails, host KV/localStorage mirrors, backend attachments or replay buffers, including under concurrent reads/writes; stale generation writes are rejected.
- Target-only doc mutation: S's image records purged, S's text/non-image metadata intact, other sessions' records intact; no whole-doc stale overwrite.
- Stale-client behavior: connected compatible client acknowledgments are required for success; incompatible connected clients fail closed before mutation; offline clients reconcile generation before reconnect hydration and cannot publish old-generation writes. Success text does not claim unreachable caches are already erased.
- Byte purge only when image-only and unreferenced; referenced/shared bytes retained.
- Unrelated session's process, history, and cache unchanged throughout.

### Browser and live-runtime acceptance

- Use a dedicated disposable Pi session/fixture, never the user's existing conversation, and do not call a paid model for the cleanup test.
- Verify initialize → create/load session → image cleanup → load the same session ID; confirm sanitized history is replayed and the image blocks are absent from the panel (within Pi 0.0.33 replay capabilities; disk preservation verified separately).
- Run two independent Pi sessions and verify cleanup of one leaves the other session process and history intact. Also test the busy-session refusal.
- In the actual browser, verify Pi-only visibility, confirmation, disabled/loading state, success count/backup path (with the non-misleading copy), failure state, focus/keyboard behavior, narrow viewport, and absence of stale previews.
- Verify the bridge process remains running throughout; no other Pi session child and no bridge is restarted; only S's child is closed/reopened.
- Run the checks required by `TESTING.md`, `AGENTS.md`, and `docs/design-system.md`; report unit/contract, protocol/gate, cache/replay, browser, and live-runtime evidence separately.

## Out of scope

- Cleaning every Pi session or any non-Pi agent.
- Deleting backups automatically; they contain the original image data by design.
- Compaction, summarization, model retries, or automatic cleanup at a provider limit.
- Claiming this feature fixes any reported upstream HTTP 400 until a subsequent request succeeds and the upstream error is observed.

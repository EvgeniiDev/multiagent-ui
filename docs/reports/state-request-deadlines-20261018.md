# Ограничение ожидания state-сервера — 18 октября 2026

## Причина и исправление

Продолжение [диагностики запуска](session-startup-diagnosis-20261018.md).
`fetchWithTimeout` прекращал отсчёт после HTTP-заголовков; последующий
`res.json()` мог ждать бесконечно. Также обработчик JSON скрывал AbortError
и мог считать HTTP 200 подтверждением незавершённой записи.

Все web-запросы KV, health и оба API мутаций используют общий
`requestRemoteJson`: 1500 мс для health, 4000 мс для остальных запросов,
включая тело ответа. Прерванный ответ не подтверждает запись.

Одинаковые снимки, поставленные в очередь до отказа, не повторяют таймаут.
Изменившийся снимок всё равно отправляется: ранний PUT мог уже записать
старые данные. Неоднозначные записи учитываются по ожидаемой серверной
ревизии и точному содержимому, сохраняются через последующие ошибки и
сбрасываются после подтверждённой записи или принятия серверного состояния.
Это не позволяет серверной дате старого записанного снимка затереть новую
сессию. Повторная запись после конфликта сохраняет CAS; при сбое чтения
нет записи без известной свежей ревизии.

Удалено промежуточное сохранение в `sessionRuntime.create`: в этот момент
новая сессия ещё не добавлена в inventory. `sessionStore.createSession`
добавляет её и сохраняет вместе с указателями открытых вкладок.

ложного успеха checked mutation после abort. Финальная версия:

  protected-field отказ без принудительной записи.
- `npm run build:web`: shared UI policy, vue-tsc, Vite — PASS.

- `scripts/test_session_startup_browser.py`: настоящий Codex ACP без prompt;

  данные, отправляет HTTP 200 и задерживает тело на 60 секунд. Проверяются
  один session/new, готовый composer, session/load после reload и той же
  сессии во втором окне. На собранной версии задержка preferences body на

Один сетевой запрос ограничен четырьмя секундами; это не четырёхсекундный
лимит всей операции создания, которая может сохранять несколько разных
снимков. Исправление ограничивает ожидание ответа и устраняет лишние записи,
но не меняет выбор local-only backend после неуспешного health probe и не
вводит постоянный журнал offline-операций для слияния между устройствами.

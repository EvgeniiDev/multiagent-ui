## Что изменено

- В `SKILL.md`, `references/delegate.md` и `references/review-acceptance.md`
  добавлены ранняя проверка настоящего API-контракта и валидных fixtures,
  первый небольшой сквозной результат вместо повторного широкого чтения,
  проверки против ложного успеха, явное состояние unknown для владения,
  разграничение доказанного дефекта и гипотезы ревьюера.
- Добавлена `porch delegate observe RUN_ID --consumer NAME`: checkpoint курсора
  хранится отдельно для каждого run/consumer; следующие вызовы получают новые
  события. Ожидание при отсутствии событий — до 60 секунд, с ранним возвратом
  при новом событии или изменении lifecycle. Вывод ограничен 20 событиями и
  500 символами data; thinking deltas по умолчанию не выводятся, но продвигают
  курсор. Для подробностей остаётся исходный `events --cursor N`.
- Конкурентный вызов с тем же consumer явно отклоняется, worker lifecycle lock
  не удерживается. Повреждение checkpoint и усечение журнала не превращаются
  в молчаливый replay. При ошибке доставки stdout cursor не продвигается.
- Курсор сохраняется после доставки: crash между доставкой и сохранением
  может повторить последнюю страницу. Это at-least-once, а не exactly-once.
  Первый вызов нового consumer начинается с cursor 0; `remaining` нужно
  дочитать. Для явного replay предусмотрен `--cursor`.

Пример для следующих запусков (RUN_ID — ID существующего разрешённого прогона):

```bash
PORCH=/home/hermes/.pi/agent/skills/pragmatic-orchestration/scripts/porch
"$PORCH" delegate observe "$RUN_ID" --consumer lead --timeout 60
```

`quiet=true` и exit 124 означают отсутствие нужного обновления до deadline,
а не отказ worker. Не добавлять после этого отдельный короткий sleep или
повторное чтение всей истории. Разные независимые наблюдатели используют
разные consumer; каждый сохраняет своё имя между вызовами.

## Границы результата

Это обновление установленного skill и его CLI. Перезапуски Compose/bridges,
изменение моделей и пользовательских сессий не выполнялись. Проверки не
доказывают production readiness всего ACP UI или измеренную экономию токенов.
Модели с уже загруженной прежней инструкцией получат новые правила при новом
чтении skill; существующие пользовательские сессии автоматически не переписаны.

`observe` ждёт события программно, но не создаёт scheduled model resume после
завершения turn. Это явно описано в инструкции. Новые содержательные события
могут вызвать ранний возврат; возможность steer посреди этапа сохраняется.
Для полностью автономного пробуждения после `agent_end` нужен отдельно
интегрированный механизм запуска turn. Эффект нового промпта и расход нужно
измерить в следующей сопоставимой рабочей сессии.

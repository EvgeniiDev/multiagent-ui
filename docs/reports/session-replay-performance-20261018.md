# Длинная история блокировала запуск следующей сессии

18 октября 2026 исправлен и выложен один подтверждённый источник медленного старта: отрисовка длинной истории чата. Runtime commit на `main`: `13b723a473292e0dbf6f5c8dd4d1f05457048820`.

Это продолжение [диагностики ожидания state-сервера](session-startup-diagnosis-20261018.md). Изменения сохранения state в этот релиз не вошли.

## Воспроизведение и профиль

В свежем Chromium открывалась сохранённая неактивная Codex-сессия `01a0f3e6-cd15-7383-860c-f7a36171decf`. Её нативный JSONL занимает 75 309 808 байт. Во всех сравниваемых прогонах браузер получил 6175 ACP-сообщений, 20 702 408 байт. После окончания replay через обычное меню «+» создавалась отдельная новая сессия.

ACP и история были настоящими, запросов модели не отправляли. KV-персистентность тестового браузера принудительно оставалась локальной, чтобы не менять пользовательские вкладки и shared-state документы. Поэтому эти измерения подтверждают ускорение обработки истории, а не исправность задержанного state-сервера.

Первый замер дал `session/load` 7,696 с и 6,644 с длинных задач основного потока, самая длинная — 4,775 с. Повтор с CPU-профилем: `session/load` 6,709 с, длинные задачи суммарно 4,652 с. Профиль относил примерно 3,57 с к `assistantItems()` и примерно 1,43 с к добавлению записей монитора трафика. На этом фоне даже следующий `session/new` выглядел медленным: браузер обрабатывал ответы с задержкой.

## Причины и исправление

В [ChatView.vue](../../src/components/ChatView.vue) для каждого tool-сегмента выполнялся `toolCalls.find(...)` по всему сообщению. У длинного агентского хода могут быть тысячи инструментов. Проверка 3000 сегментов зафиксировала 4 501 500 чтений массива. Теперь индекс инструментов строится один раз на проекцию сообщения. Сохраняются первый элемент при дублирующемся ID, ссылки на объекты, порядок текста/инструментов/вложений/плана и последний элемент. Индекс пересоздаётся при следующей отрисовке, поэтому обновления инструментов не застревают в кеше.

В [traffic.ts](../../src/stores/traffic.ts) каждая запись добавлялась в глубоко реактивный массив, после 500 записей выполнялось реактивное копирование последних 500. Это происходило и при закрытом мониторе. Теперь снимки JSON остаются обычными объектами, а реактивно заменяется только ограниченный массив через `shallowRef`. Замена корня на каждом событии сохраняет обновления UI, включая первые записи и события после достижения лимита. Подход соответствует [документации Vue о больших неизменяемых структурах](https://vuejs.org/guide/best-practices/performance#reduce-reactivity-overhead-for-large-immutable-structures).

Микрозамер добавления 6175 записей трафика: 1218 → 59 мс. Порядок, лимит 500, pause/resume, фильтры, поиск, очистка и раскрытие JSON проверены отдельно.

## Сопоставимые браузерные замеры

| Показатель | До, production HTTP | Кандидат HTTP | После выкладки, production HTTPS |
|---|---:|---:|---:|
| `session/load` | 7,678 с | 3,769 с | 3,843 с |
| Start → готовый новый чат после истории | 9,223 с | 1,626 с | 1,407 с |
| Самая длинная задача браузера | 2,811 с | 1,050 с | 0,857 с |
| Суммарное время длинных задач | 3,928 с | 1,412 с | 1,129 с |

Это отдельные прогоны одного сценария, не p95 и не обещание такого ускорения каждого запуска. Контрольный HTTP-кандидат ускорил следующий старт примерно в 5,7 раза. После выкладки второй HTTPS-прогон дал 3,798 с для истории и 1,418 с для нового чата; ошибок JavaScript и JSON-RPC не было.

После этого обновили страницу с двумя открытыми сессиями — исторической и новой. Оба `session/load` успешно завершились (3,167 и 0,371 с), активный URL и доступный composer восстановились. Общая маршрутизация и мосты не менялись.

# Задержки запуска сессий: диагностика 18 октября 2026

Production-код не изменён. Экспериментальное исправление отклонено после проверки восстановления сессии; его исходники и диагностические инструменты сохранены в `/tmp/acp-start-diagnosis-20261017/`. Этот отчёт описывает установленные механизмы задержек, а не завершённое ускорение.

## Что удалось измерить

Предыдущие 0,6 с для Codex измеряли создание сессии через работающий ACP-процесс, без полного браузерного пути. Это не типичное время запуска и не оценка редких медленных случаев.

18 октября пять последовательных `session/new` в работающем процессе Codex заняли 68, 92, 76, 84 и 85 мс. Чередовались пустой тестовый каталог и каталог проекта. Четыре запуска отдельных новых процессов адаптера заняли суммарно 3,583; 1,000; 1,031 и 1,235 с. Действующий bridge не перезапускался; запросы моделям не отправлялись.

В двух запусках с измерением внутренних RPC проверка аккаунта занимала примерно 0,52–0,57 с, `thread/start` — 91–129 мс, `model/list` — 5 мс. Эти замеры не воспроизвели внутренний старт Codex длительностью около 15 с.

## Подтверждённая задержка до обращения к Codex

В настоящем Chromium открывалась обслуживаемая production-сборка на `http://127.0.0.1:25808/chat`, затем через «+» создавалась отдельная тестовая сессия Codex. ACP оставался настоящим. Документы state направлялись в отдельный HTTP-сервер в памяти; пользовательские документы и карточки не менялись.

Тестовый сервер отправлял заголовки HTTP 200 для PUT `preferences.json` сразу, а JSON-тело — через восемь секунд. Нажатие Start → готовый чат заняло **8,9 с**; собственно `session/new` — **157 мс**. WebSocket открылся лишь после ожидания сохранения настроек.

Причинная цепочка:

1. `NewSessionMenu.start()` ожидает `prefs.save()` для последнего выбранного каталога до вызова `sessionStore.createSession()`.
2. `RemoteKVStore.save()` ставит PUT в последовательную очередь и ожидает его завершения.
3. `fetchWithTimeout()` снимает AbortController-таймер после `fetch()`, то есть после получения заголовков.
4. `putRemote()` читает `res.json()` уже без таймера. При остановившемся теле ответа время ожидания не ограничено.
5. До завершения этого ожидания запрос к Codex вообще не отправляется. Пользователь видит медленный старт агента.

Тот же шаблон есть в health probe, чтении state-документа и старом `mutateRemoteDoc()`. После `session/new` runtime дополнительно ожидает сохранения сессий перед переходом в connected; следующий save выполняет session store.

Код: [меню запуска](../../src/components/NewSessionMenu.vue), [runtime](../../src/lib/sessionRuntime.ts), [state storage](../../src/lib/host/storage.ts).

## Почему простая замена таймаута недостаточна

Временный вариант перевёл чтение JSON на существующий `requestRemoteJson()`, проверял AbortSignal после чтения и не считал незавершённое тело успешным сохранением. Три проверки сначала воспроизвели бесконечное ожидание, а после изменения прошли: health — около 1,5 с, GET/PUT документа — около 4 с.

Однако браузерный тест с таким вариантом всё ещё занял **9,674 с**: несколько сохранений уже стояли в очереди и каждое отдельно повторяло таймаут. Проверка `down` находилась до постановки в очередь; уже ожидающие задания не проверяли состояние повторно.

Вариант с проверкой `down` внутри очереди сократил старт до **4,788 с** при задержке preferences и **4,930 с** при задержке sessions. Но он провалил следующий пользовательский шаг: обновление страницы после создания сессии. Последнее сохранение sessions могло быть пропущено после таймаута предыдущего. Локальный mirror содержал новую сессию, сервер — старую версию документа. При reload серверная копия вытесняла локальную, и новый чат не восстанавливался.

Поэтому эти цифры не являются результатом выпущенного ускорения. Вариант не выложен.

## Что необходимо сохранить при исправлении

- Таймаут должен охватывать и заголовки, и тело JSON. Прерывание чтения после HTTP 200 не является успешным подтверждением сохранения.
- Очередь не должна повторять одинаковые неудачные сохранения, но обязана различать их и более новые изменения, ещё не отправленные серверу.
- После неоднозначного результата PUT нельзя определять подтверждение содержимого только по времени: сервер мог сохранить старый запрос после появления более новых локальных правок.
- Неподтверждённые изменения должны переживать reload. Подтверждение одного окна не должно стирать признак неподтверждённых изменений другого окна.
- Нужны проверки: зависшее тело; несколько ожидающих сохранений; новое изменение во время PUT; reload сразу после создания; два окна; восстановление после возвращения state-сервера. Одних быстрых ACP RPC и зелёных unit-тестов недостаточно.

Это задача согласования локального mirror, очереди и подтверждённой серверной ревизии, а не только увеличение таймаута или ускорение Codex.

## Проверки и ограничения

- Проверки зависшего тела и очереди воспроизведены до экспериментальных изменений. Частичные исправления проходили unit-проверки, но не полный браузерный сценарий создания и reload.
- Чистая web-сборка, TypeScript и shared UI policy проходили. Изолированная сборка не публиковалась; мосты не перезапускались.
- Старый `e2e_state_backend.py` остановился на отсутствующем в нынешнем UI `.scope-select`. `test_view_routes.mjs` имеет четыре падения из-за отсутствующего `window.matchMedia` в тестовом окружении; они подтверждены и на исходном коде без эксперимента. Это не доказательства исправности или поломки затронутого state-пути.
- Редкий медленный запуск именно внутри Codex пока не воспроизведён. Исходный пользовательский эпизод не привязан к сессии и трассе браузера. Подтверждён отдельный механизм задержки на стороне интерфейса и state-сервера.
- Все экспериментальные изменения runtime сняты. В commit входит только этот отчёт.

# Fusion: панель разных моделей + судья + интегратор

---

## Что это

Одну задачу параллельно решают 2–10 **разных** моделей. Отдельная модель-судья
сравнивает ответы и пишет «наряд на работу» — короткое ТЗ. Единственная модель,
меняющая файлы (интегратор), работает строго по наряду.

Три этапа: **панель → судья → интегратор**.

## Этап 1. Панель

- Все панелисты получают одинаковый текст задачи, стартуют одновременно.
- **Не видят ответы друг друга.** Дебаты (читать чужое + спорить N раундов) — негодный
  вариант: модель подстраивается под чужой уверенный ответ, даже неверный.
- Только читают проект, ничего не меняют. Иначе получишь N версий одного кода.
- Включён веб-поиск: одна модель помнит библиотеку годичной давности, другая проверит
  текущее состояние — расхождение всплывёт у судьи.
- Формат ответа панелиста (контракт): что предлагает / почему / какие файлы затронет /
  минусы решения / чего делать не стал бы.

## Этап 2. Судья

- Только сильная модель. Свой ответ на задачу не пишет — только сравнивает.
- 5 пунктов сравнения:
  1. в чём ответы совпали;
  2. где прямые противоречия;
  3. что разобрал только один, другой пропустил;
  4. уникальные идеи каждого;
  5. **слепые зоны** — важно для задачи, но нет ни у кого (чаще всего именно эта
     строка усиливает итоговый план).
- Совпадение ≠ правота: обе могут ошибиться одинаково. Судье разрешено самому открыть
  код и проверить спорное место, чтобы не судить галлюцинацию.
- Выход судьи — не «сравнение», а **наряд**: цель, что входит / что не входит, критерии
  приёмки, шаги, где в коде. Победителя не выбирает — только объединённое решение.
  (Ошибка первой версии автора: судья останавливался на сравнении, а решение заново
  принимал кодер с меньшим контекстом.)
- Режимы выхода: вопрос / план / ревью → ответ сообщением, кода нет; агент / поиск
  бага → дальше идёт интегратор с изменением файлов.

## Этап 3. Интегратор

- Получает **только** наряд. Ответы панели ему не показывать — иначе начнёт заново
  судить и галлюцинировать.
- Решение не пересматривает. Исключение одно: наряд противоречит реальному коду —
  тогда правит по факту кода.
- В конце сверяется с критериями из наряда и отчитывается: что сделано, где, где
  отступил от плана.

## Когда брать, когда нет

- Цена: минимум 4 прогона вместо 1 (2 панелиста + судья + интегратор). Работу
  НЕ ускоряет.
- Брать: несколько разумных решений; цена ошибки — часы/дни; нужна многогранность
  (архитектура, баг с неочевидной причиной).
- Не брать: нужна скорость или задача бьётся на части → оркестратор / соло.

## Классификация схем объединения (из видео)

1. Выбор лучшего — просто, но полезное из проигравших выбрасывается.
2. Дебаты — конформизм, не работает.
3. Панель + сведение — этот режим.
4. Маршрутизация по сложности (простое — дешёвой, сложное — дорогой) — в каждый момент
   работает одна.

## Что из этого — в acp-ui

- Судья с нарядом ≈ наш чекер ревьюера + severity-гейт: вердикт по каждой находке,
  дальше только подтверждённое.
- Запрет «интегратор не видит панель» ≈ наше «субагенты отдают артефакты-файлы,
  а не саммари в контекст».
- Пункт «слепые зоны» — кандидат в критерии чекера.
- Контракт ответа панелиста (предложение/почему/файлы/минусы/не делать) — готовый
  шаблон промпта для параллельных ролей.

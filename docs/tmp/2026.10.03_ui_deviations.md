## D2 — `PrepCompletenessItem` type did not match the server wire shape

- Evidence: `server/execution/preparation/session.mjs`
  `completenessView()` returns per-kind STATE STRINGS
  (`absent|draft|presented|confirmed|approved`), counts for
  assumptions/decisions, an object for openQuestions. `src/lib/execution/
  api.ts` typed `ExecPrepView.completeness` as
  `Record<string, PrepCompletenessItem>` (object-only), and
  `PreparationPanel.presentedLine()` read `c?.stale`/`c?.approved` —
  fields the server never sends. A `draft` doc with a `confirmed` state
  would have rendered misleadingly.
- Resolution: added `PrepCompletenessState` / `PrepCompletenessCounters` /
  `PrepCompletenessValue` types; `completeness` is now
  `Record<string, PrepCompletenessValue>`; panel reads the authoritative
  state string plus a server-counters line (`prep-completeness` testid).
  No backend touched.
- Remaining risk: none known; covered by unit tests (slice 1).

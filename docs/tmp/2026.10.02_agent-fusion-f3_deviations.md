# Agent Fusion F3 — deviation journal

Unit: F3 — judge + versioned work order + two results (R6–R9; KTD5–KTD6).
Depends on: F2 panel + partial failure (accepted), U5 core gates (accepted).
Scope guard: no F4 UI, no orchestrator/swarm/idea, no merge/push/publish.

Format per entry: expected vs observed, evidence (file/command), why a
change was needed, action taken, remaining risk. Resolved entries stay
in place.

## Design decisions recorded up front (not deviations)

- Judge/integrator attempts reuse `run.attempts` with roles
  `judge`/`integrator` and phases `judge`/`integrate` (added to
  `RUN_PHASES`). They mint through dedicated internal commands
  (`judge_begin`, `integrate_begin`) because `begin_attempt` is bound to
  the solo porch launch surface (phase/cwd/workspace) exactly like the
  F2 `panel_begin` reasoning.
- The work order is a durable, versioned artifact:
  `run.fusion.workOrders[]` (`wo_v1`, `wo_v2`, …) bound to a committed
  `work-order` artifact of the producing judge attempt. The domain
  re-parses the artifact bytes at resolve time — the controller's parse
  result is never trusted (same rule as panel answers).
- `approve_work_order` is a USER command (commandId +
  expectedControlRevision). It is legal only while the run carries a
  matching `pendingActions` entry `{type:'work_order_approval',
  versionId}` — a stale/foreign version id or hash refuses.
- Document result: judge mints WO → run parks `blocked` with a
  work-order-approval pending action → `approve_work_order` completes
  the run `succeeded` with `run.result = {kind:'document', workOrder}`.
  The WO can be attached to requirements/plan via
  `attach_document` source `{type:'work_order', runId, versionId}` —
  that creates a NEW document version with NO approval (the existing
  attach semantics already guarantee this).
- Implementation result: requires approved requirements+plan at start
  (existing `requireApprovedInputs`); `fusion.review{reviewer,checker}`
  and `fusion.integrator` become mandatory spec fields. The judge
  verdict `in_plan` + unchanged approved inputs auto-routes the run to
  phase `integrate`; `scope_change`/`uncertain`/changed inputs park the
  run `blocked` + work-order-approval pending action.
- Integrator isolation (R2/KTD4): `integrate_begin` whitelists input
  names (`task`, `work-order`, `requirements`, `plan`, `design`,
  `results`) and binds each sha256 to a durable source (task doc sha,
  work-order artifact sha, run.inputs.* sha). ANY declared input sha
  equal to a committed `answer`-kind artifact hash is refused — panel
  evidence can never enter integrator materials by construction, not
  just by prompt wording.
- The integrator's imported result lands in the managed workspace
  (canonical→ws copy, `.git` excluded) so the U5 snapshot/checks/
  reviewer/checker pipeline consumes it unmodified — reviewer and
  checker receive validation copies and can never touch the accepted
  workspace. `record_integrate_result` binds the canonical import
  evidence (treeSha/commitSha/changed) to the run before
  `awaiting_validation`.
- Post-check edits: the driver recomputes `computeResultManifest` on the
  bound workspace while the run is `awaiting_acceptance`; a result-hash
  drift sends `annul_acceptance` → run back to `awaiting_validation` →
  a fresh validation round.
- Fix cycles on implementation runs re-enter as integrator attempts
  (`fixContext` → `integrate_begin` with `fix:true`, private repo
  seeded from canonical HEAD via `materials.fromCanonical`), one fix
  attempt per recorded fixContext.
- Deviation from task text: there is no `prompts/execution/fusion/`
  directory in this codebase — fusion prompts are code-built
  (`server/execution/fusion/prompt.mjs`). Judge/integrator prompts live
  in `server/execution/fusion/handoff-prompt.mjs` to match the actual
  convention.

## Deviations

### D1 — `bind_attempt` clobbered `run.phase` for fix integrator attempts (REAL BUG, fixed)

- **Expected:** after the U5 gate writes `fixContext`, the fix integrator
  attempt binds → resolves → `record_integrate_result` (fix path) →
  `awaiting_validation` → new validation round.
- **Observed:** run stuck `active`/`awaiting_validation` forever;
  `importAndMaterialize` retried `record_integrate_result` every tick and
  every send threw `phase_mismatch` (`wantPhase='awaiting_validation'`,
  actual `'integrate'`). Evidence:
  `node --test --test-name-pattern="fix round" scripts/test_fusion_handoff.mjs`
  — run dump `{"s":"active","ph":"integrate","rounds":[{"r":1,"d":"fix"}]}`.
- **Root cause:** `cmdBindAttempt`
  (`server/execution/execution-domain.mjs`) wrote `run.phase = att.phase`
  unconditionally. A fix integrator mints with `att.phase='integrate'`
  while the run must stay `'awaiting_validation'` — the bind overwrote the
  phase. For panelist/judge/initial-integrator attempts the write was a
  harmless no-op (phases coincide); only the fix attempt diverged.
- **Fix:** `cmdBindAttempt` no longer writes `run.phase` for roles
  `panelist`/`judge`/`integrator` — fusion commands own run.phase exactly
  like they own run.status on resolve (fusion resolves already forbid
  `runStatus`/`runPhase`). `run.status = 'active'` on bind kept — it is
  always already true on the fusion path.
- **Risk:** none — F2 suite re-verified 11/11; U5 domain suite (which
  exercises reviewer/checker binds, non-fusion roles still write phase)
  29/29.

### D2 — `expectedInternalRevision` required on internal commands (test fix)

- **Expected:** forged `integrate_begin` through `createInternalClient`
  reaches the domain and is refused on input checks.
- **Observed:** `400 bad_command — internal commands require
  expectedInternalRevision` before any domain logic. The scheduler's
  `send()` carries the CAS revision from its cached card — the test
  helper now reads `card.internalRevision` first
  (`scripts/test_fusion_handoff.mjs`, `internalCmd`).

### D3 — `ACP_EXEC_VALIDATION` env gate missed in the fake scheduler (test fix)

- **Expected:** fusion implementation runs ride the U5 validation surface
  after `record_integrate_result`.
- **Observed:** `run.validation` never materialized; run parked
  `active`/`awaiting_validation` — `createManagedScheduler` defaults
  `validationEnabled` off (`env.ACP_EXEC_VALIDATION === '1'`). `mkSched`
  now passes the flag; without it the U5 gate is silently inert — exactly
  the kind of "looks green, never gated" gap the journal exists for.

### D4 — fake proc-runtime registry incomplete (test fix)

- **Observed:** reviewer attempt stuck `launching`, event tail
  `launch_blocked: registry_scan_failed — Cannot read properties of
  undefined (reading 'values')`. The hand-rolled
  `registry = { procs: new Map() }` lacked `runs`/`records`/`usedAttempts`/
  `unreadable`/`listFails`/`seq` that `createFakeRuntime`'s `reconcile()`
  scans. `mkSched` now builds the full shape (same as
  `u4_core_selftest.mjs`'s registry literal plus `unreadable`/`listFails`).

### D5 — test-side fixture bugs in `scripts/test_fusion_handoff.mjs`

All test-harness, no product code:

- `canonicalPrepare` in the fake container runtime cloned
  `p.projectRoot` directly — but `projectRoot` is the **mount basename**
  (`projectKeyFor`), not a filesystem path (`git clone` spammed
  `repository 'f3-proj-…' does not exist` every tick). The fake now
  resolves `projectRoot === projectKeyFor(env.projectDir)` →
  `env.projectDir`, mirroring the real env-controller's projects-root
  resolution.
- Behavior keys used `ja-${runId}-nN` but attempt ids are minted
  `ja-${run.id.slice(4)}-nN` (no `run_` prefix) — judge attempts fell
  through to `default` behavior and failed with
  `work_order_incomplete` on a panelist answer template.
- `roleDocs` round parse read `params.cwd.split('/').at(-1)` — for
  reviewer/checker the cwd is `<valDir>/{review,check}` so round always
  defaulted to 1; round-2 report docs failed the `record_report` round
  binding. Now parses the `val_<run>_<n>` path segment.
- Assertion updates matching durable contract codes:
  `run_not_launchable` accepted for a blocked run's forged
  `integrate_begin`; validation report artifacts commit as
  `kind:'evidence'` (file names carry the role tag), not
  `kind:'findings'/'verdicts'`; post-annul phase sampling accepts any
  validation phase (round 2 may already be in `verify`).

### D6 — F2 semantics preserved (resolved earlier, kept)

- `judgeEligible` must stay `outcome === 'complete'` (panel is
  judge-ready), NOT `&& !!fz.judge` — otherwise three F2 tests fail
  (parallel completion, exclusion quorum, retry completion). When a
  judge IS configured the run moves `active`/`judge`; without one it
  stays blocked with the eligibility flag true.
- Exclusion-triggered settling into judge phase must also clear
  `run.finishedAt` — a `blocked` run reopening to `active` cannot keep a
  terminal timestamp.

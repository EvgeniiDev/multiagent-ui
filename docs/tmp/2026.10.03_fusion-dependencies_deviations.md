# Fusion dependency setup integration — 2026-10-03

Implementation runs may declare `fusion.setupId`, a safe registered setup ID (1–128 characters, first character alphanumeric; remaining characters alphanumeric, dot, underscore, or hyphen). Document runs reject setup declarations. The accepted setup is stored in the durable Fusion run, included in its reuse fingerprint, and carried through continuations. Registration and approved setup commands remain controller-owned; the run never carries arbitrary package-manager argv.

Only integrator and fix workers receive dependency mounts. Panelist and judge roles retain their declared `deps:false` policy.

Before an integrator attempt is minted, the handoff driver calls `runtime.prepareDependencies({setupId,canonicalId})` after canonical preparation. A proven result becomes the immutable `attempt.launch.dependencies` descriptor `{setupId,depSetId,lockHash,snapshotSha}`; role materials include its setup ID, dependency-set ID, and lock hash, so the materials digest binds the mounted set. A recovered launch rebuilds from that durable descriptor instead of preparing a potentially different dependency set. Unavailable preparation holds the phase without consuming a new attempt.

After private-repository import and workspace materialization, the driver prepares dependencies from the canonical's imported HEAD again. The domain accepts `record_integrate_result.dependencies` only when it binds the declared setup and the exact imported commit. It persists `fusion.integrate.dependencies` with the import before the run can enter verification. Changed lockfiles therefore replace the initial set. Temporary setup failures retry without granting verification readiness.

For setup-declared fix rounds, the domain retains fixContext until the imported dependency proof is committed. This closes the existing shared scheduler shortcut that could otherwise start a new validation while a completed fix still awaited import/preparation. No-setup runs keep the previous flow.

## Companion integration contract

- ENV's runtime helper must accept and forward canonicalId (the first helper version only forwarded pinned project fields). Controller `deps.prepare` now accepts canonical sources and returns canonicalId/snapshotSha.
- The shared validation scheduler must require `fusion.integrate.dependencies.snapshotSha === fusion.integrate.import.commitSha` whenever setupId is declared, and expose that prepared set coherently to actual validation copies/check execution. The descriptor is available before awaiting_validation. This mounting/gate work belongs to the backend scheduler owner; no shared scheduler files were edited here.
- The UI owner added an optional registered setup ID field for implementation runs. Server validation uses the same safe-ID length and alphabet.

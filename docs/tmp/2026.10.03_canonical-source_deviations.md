# Canonical source binding

The controller previously verified every supplied source commit in the original project before selecting a canonical source. A fix commit created only in the controller's registered canonical repository therefore failed admission despite being the intended source. Fusion also supplied its original base commit while requesting the current canonical tree, leaving the recorded source different from the copied bytes.

For a private repository with `materials.fromCanonical: true`, the controller now resolves `materials.canonicalId` through its durable canonical registry first. The registered project must match `materials.projectRoot`, the canonical tree must be clean, and `materials.snapshotSha` must equal its current HEAD. This source cannot be combined with `snapshotId`. The archive reads the verified SHA rather than mutable HEAD. The immutable snapshot route for other launches remains available.

Fusion fix admission reads the actual `canonical.status.canonical.head`, records it in `attempt.launch.snapshotSha`, and uses that saved binding when reconstructing launch materials. Dependency preparation must refer to the same commit. No caller workspace path or new RPC was introduced.

Two real temporary Git repository regressions failed before the controller repair: a canonical-only commit was rejected, and a stale source commit was accepted. They now cover successful byte/tree transfer and rejection of stale HEAD, wrong project, unknown canonical, and dirty canonical trees before Docker creation. The existing Fusion fix regression likewise failed before its launch source was persisted and now verifies that the source is the prior imported canonical commit.

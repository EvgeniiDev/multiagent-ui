# Agent Fusion F2 — deviation journal

Unit: F2 — panel phase + partial failure (R1, R3–R5, R9; KTD5–KTD6).
Depends on: F1 environment + access boundaries (accepted).
Scope guard: no F3 judge/work-order, no F4 UI, no orchestrator/swarm/idea.

Format per entry: expected vs observed, evidence (file/command), why a
change was needed, action taken, remaining risk. Resolved entries stay
in place.

## Design decisions recorded up front (not deviations)

- Panel attempts reuse the existing `run.attempts` machinery
  (bind/cancel/observe/resolve/heartbeat/slot accounting) with
  `role:'panelist'` + `participantId` + phase `'panel'`. Creation goes
  through a dedicated internal command `panel_begin` — the generic
  `begin_attempt` is role/phase/workspace-bound and single-live-attempt,
  none of which fit a parallel panel.
- Run-level authority for fusion runs (needed by complete_run /
  panel_settle before any attempt exists — e.g. an incompatible
  composition rejected before the first launch) is established by a new
  internal command `panel_claim` → `run.fusion.owner`. `complete_run`
  falls back to that owner when no attempts exist yet.
- F2 terminal states: when no executable work remains the run goes
  `blocked` with a distinguishing `run.fusion.status` —
  `decision_pending` (a participant awaits retry/exclude; the user
  commands reactivate the run), `complete` (quorum of ≥2 models among
  accepted answers; the judge phase is F3 scope — nothing further can
  execute), `quorum_failed`. The run stays `active` while any
  participant has live or launchable work, and carries
  `run.fusion.pendingActions` while a decision is owed.
- `retry_participant` grants exactly ONE extra attempt
  (`extraAttempts += 1`) — "no automatic third attempt" holds and each
  retry is an explicit durable user decision.
- `exclude_panelist` accepts only `awaiting_decision` participants and
  refuses when the remaining non-excluded participants would span fewer
  than 2 distinct model identities (`panel_below_minimum`). Exclusion is
  recorded on both the participant and `run.fusion.exclusions` (the
  judge-facing list).
- Answer reuse across `continue`: carried only when the new run's
  fingerprint (task sha + project root + snapshot sha + search flag +
  resultKind) equals the previous run's AND the participant's
  profileDigest is unchanged. Any input change ⇒ fresh panel.

## Deviations

### D1 — `panel_settle` commandId replay collision (found via deterministic suite)

- **Expected:** after `retry_participant` reopens a participant and its new
  attempt answers, the driver re-settles the panel to `complete`.
- **Observed:** the run stayed `active`, `fusion.status` stayed `open`
  forever. Evidence: live debug trace showed `panel_settled` tick tags every
  pass while `fz.settledAt` remained unset.
- **Cause:** the settle command id was `ps-<runId>-by-<instanceId>` — fixed
  per run. The first settle (outcome `decision_pending`) recorded that
  commandId durably; every later settle — after the participant state
  legitimately changed — reused the same id, so the command layer replayed
  the stored first result and never executed the new decision.
- **Action:** the settle commandId now carries a sha256 signature of the
  durable participant state (`id:status:attemptsUsed` per participant) —
  `server/execution/fusion/controller.mjs` step 4. Identical state replays
  idempotently; any participant change mints a fresh command.
- **Why needed:** settle is the panel's only terminalizer; a replayed stale
  verdict silently deadlocked every post-decision recovery.
- **Remaining risk:** none identified — a crash between two different-state
  settles produces two distinct commands (both durable); replay of either is
  safe since the domain re-derives the outcome and ignores the caller's claim.

### D2 — cancel racing the launch handshake left attempts un-drainable

- **Expected:** a `cancel_attempt`/`stop` intent on a `launching` attempt
  reaches a terminal state.
- **Observed (code audit, not a suite failure):** an attempt in
  `cancelling` with `porchRunId === null` never re-entered the reconcile
  path — `superviseAttempt` routed only `launching` — and `observePanelist`
  waited on a run id that could never be bound. The run could not drain.
- **Action:** `superviseAttempt` now routes `cancelling && !porchRunId`
  into `reconcileLaunch`; inside it, the no-evidence branch resolves
  `cancelled` directly (never re-issues a start for a cancelled attempt),
  while a found record still binds normally (the next pass observes and
  cancels it).
- **Remaining risk:** the `launch_uncertain` sub-window (record exists,
  phase `launched`, bind lost, then cancel) is covered by the same path —
  bind then observe→cancel — verified by the crash-window suite entry.

### D3 — search gate only fired while `run.attempts` was empty

- **Expected:** every panelist's first attempt is gated on its full-profile
  capability proof.
- **Observed (code audit):** the gate ran only when the whole run had zero
  attempts. A partial `panel_begin` (p1 minted, p2 refused by a transient
  slot/parse error) would let p2 launch un-gated on the next pass.
- **Action:** the gate now fires whenever a `pending` participant has no
  attempts yet (`unstarted`), independent of run-level attempt count.
- **Remaining risk:** none — `searchGate` no-ops when search is disabled
  and re-checks every non-excluded participant's digest each time it runs.

### D4 — u3_core_selftest cross-scheduler flakiness (pre-existing, not F2)

- **Observed:** two u3 tests (`attemptId is globally unique…`,
  `global + role slot limits…`) fail intermittently in full-suite runs —
  `run_not_launchable` on an `interrupted` run / `starts(B)==1`. Each passes
  deterministically in isolation (`--test-name-pattern`), and the moving
  failure set differs between runs (42/43 vs 41/43).
- **Mechanism (verified):** `createFakeRuntime` uses the real `process.pid`
  for every instance while `registry.procs` is per-runtime. A second
  scheduler's tick legitimately adopts a foreign attempt via the
  `process_dead` proof; if the adopted attempt is still `launching` (bind
  raced the next tick) the reconcile path re-issues `runtime.start`, or a
  vanished registry record resolves `interrupted`. All of that is U4
  adoption machinery — F2 changes are additive and gated on
  `run.mode === 'fusion'`; solo `begin_attempt`/adoption paths are
  untouched.
- **Action:** documented; no F2 code change. The race exists in the test
  harness/fake, not in production semantics (a real remote runner's pid is
  not the scheduler's own pid).
- **Remaining risk:** the u3 suite is not a reliable gate until the fake
  gives each scheduler a distinct proc namespace or shares a registry — a
  test-infra fix outside F2 scope.

### D5 — test harness artifacts (self-inflicted, fixed)

- Fake container runtime initially emitted `prun-N` run ids — rejected by
  `RUN_ID_RE` (`run_` prefix) so `bind_attempt` never landed (mass
  `launching`/`queued` failures). Fixed to `run_pN`.
- A scratch debug script dropped `headers` in the injected transport, so
  the internal token never reached the service (401 `internal token
  required`). The real suite's `mkClient` forwards headers — harness-only
  bug, no production impact.

### D6 — u3 flake root-caused and FIXED in the fake runtime (supersedes D4's "no fix" verdict)

- **Acceptance blocker:** `node --test scripts/u3_core_selftest.mjs` failed
  1–2 of 43 intermittently. Current-tree repro before the fix: **7 of 12
  runs failed** — `attemptId is globally unique across runs and cards`
  (`begin_attempt` → 409 `run_not_launchable`: the run had been resolved
  `interrupted`) and/or `global + role slot limits are authoritative
  across cards` (`starts(B)==1` ≠ 0: B launched under global cap 1). The
  failing pair is one mechanism with two outcomes; which of the two
  assertions tripped depended on an independent coin flip per attempt.
- **Baseline limitation (explicit):** there is NO clean-HEAD baseline for
  this suite. `server/execution/managed-scheduler.mjs`,
  `execution-domain.mjs`, `state-service.mjs`, `scripts/u3_core_selftest.mjs`
  and the rest of U2–U7 are untracked working-tree files on top of
  fb0a298 (U1); `git show HEAD:<file>` is missing for all of them, so
  `git stash -u`/a HEAD worktree would delete the scheduler and the test
  rather than revert them. The baseline actually run: a copy of the
  working tree with every F2 hunk surgically reverted (`fusion/` deleted;
  `createPanelDriver` import/dep/`run.mode==='fusion'` branch/driver
  wiring out of the scheduler; `FUSION_*` gates, `panel_*` internal
  commands, `cmdStartFusion`, fusion-continuation, panelist/panel-owner
  legs out of the domain; the `fusion` flag out of the state service).
  On that F2-stripped tree the suite failed **identically — 4/5 runs,
  same signatures**. Independently, every F2 hunk that survives in
  shared files is gate-dead here (`run.mode==='fusion'`,
  `features.fusion` default-off, `fusion` dep null) — no F2 code executes
  in this suite. Verdict: **pre-existing flake, proven two ways**.
- **Root cause (harness layer, not runtime product code):**
  `createFakeRuntime.environment()` returns `pid: process.pid` for EVERY
  instance while `registry.procs` is per-runtime and never contains it
  (fake-runtime.mjs `environment()`/`processIdentity`). Two default-env
  schedulers in one test process therefore share an identical
  envKey/envInstance AND a recorded owner pid that the peer's /proc model
  reports as clean ENOENT: `adoptionProofFor` mints a valid
  `process_dead` proof on a LIVE owner → `adopt_attempt` → the bound
  porchRunId is absent from the adopter's private `registry.runs` →
  `supervisor_vanished` → the recorded supervisor pid is absent from the
  adopter's `procs` → "positively dead" → `resolve_attempt interrupted`
  + `complete_run interrupted` (managed-scheduler.mjs:2273-2331,
  2083-2168). In production a same-env peer probing the recorded owner
  pid in a real /proc would see it ALIVE and stay hands-off — the fake's
  procs table was missing the one row every real /proc contains: the
  probing process itself. The u4/u5/fusion helpers already compensate by
  assigning each instance a distinct pid AND registering it alive in the
  shared procs table (u4 mkSched ~L121-145, u5 ~L190-200,
  test_fusion_controller ~L348-355); u3's `mkSched` does neither — that
  asymmetry is why only u3 flakes.
- **The flaky coin:** whether `att.supervisor` is durably recorded in the
  launch tick (`tryLaunch` bind → `runtime.status()` → `observe_attempt`,
  managed-scheduler.mjs:1435-1452). `supervisorIdentity` returns null on
  `st.terminal` (L1476), and the fake arms a REAL 5ms outcome timer
  (`scheduleOutcome`, fake-runtime.mjs). If the command-queue/fs latency
  between `runtime.start` and `runtime.status` exceeds ~5ms the run is
  already `completed` → no supervisor identity → the adoption still
  happens but the vanish-resolve falls to `missing_identity` and retains
  instead of terminalizing → green run. Repro evidence
  (/tmp/repro-u3.mjs, 20 fresh envs): sup recorded → `adopted-resolved` +
  run `interrupted`; sup null → `adopted-vanished` + run stays `active`;
  18/20 interrupted before the fix.
- **Fix (product test-infra, no test weakened):** `fake-runtime.mjs`
  seeds `registry.procs[environment().pid]` as
  `{exists:true,state:'R',readable:true,starttime,pidNs}` at
  construction — the exact identity `environment()` advertises — and
  NEVER overwrites an existing row (scripted death/EACCES entries stay
  authoritative). Same-env peers now read the recorded owner pid alive →
  `adoptionProofFor` returns null → `foreign` hands-off, deterministically
  independent of the 5ms timer. No assertions, timeouts, or test logic
  changed; the scheduler and domain are untouched.
- **Verification (all on the real tree):**
  - `node --test scripts/u3_core_selftest.mjs` → **43/43 × 5 consecutive
    runs** (was 7/12 failing).
  - 20-iteration scenario repro → 0/20 interruptions (was 18/20).
  - `node --test scripts/test_fusion_controller.mjs` → 11/11.
  - `node --test scripts/u4_core_selftest.mjs` → 61/61.
  - `node --test scripts/u5_domain_selftest.mjs` → 29/29.
  - `node --test scripts/test_execution_environment.mjs` → 82/82 checks.
  - Adjacent fake consumers: u1_runtime 19/19, u2_state 34/34,
    u5_core 31/31, u5_runner_wiring 1/1, test_sfc_loader 1/1.
- **Remaining risk:** low. Tests that must model a DEAD controller pid
  already set `procs.set(pid,{exists:false})` explicitly after
  construction (u3:352/412/450/1444, u4/u5 instPid kills) — the `!has`
  guard preserves those. The seed only covers the pid the runtime itself
  claims; foreign pids in private registries still read absent by design.
  Residual conceptual gap (unchanged, pre-existing): a private-registry
  pair can never model "shared /proc namespace" — suites needing
  cross-instance proc visibility should keep the u4 shared-registry
  convention. D4's mechanism note was directionally right; its
  "test-infra fix outside F2 scope" risk is now closed.

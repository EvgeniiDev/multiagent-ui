# Fusion lifecycle repair — 2026-10-03

Fusion panelist, judge, and integrator supervision incorrectly treated observer timeouts as terminal failures, suppressed cancellation retries after unsuccessful requests, and expected nested launch records that the constrained runtime does not return. Fresh and recovered starts also lacked the durable stop fence used by Core.

Both drivers now require an explicit terminal wait outcome before resolving a bound attempt. Observer timeouts retain supervision and still trigger durable timeout cancellation when the participant deadline expires. Cancellation is deduplicated only after `ok:true, requested:true`; failed requests remain retryable.

Launch reconciliation consumes flattened `phase`, `porchRunId`, `error`, `createdAt`, and `launchStartedAt`. Nested records remain accepted for compatibility, but the controller and handoff integration adapters now expose flattened runtime fields. Missing evidence must be affirmative (`missing:true`); an exception, null response, or corrupt record grants neither a fresh launch nor cancellation completion. A thrown start is uncertain until durable runtime evidence resolves it. Registry binding requires a successful scan with exactly one matching run; multiple matches retain reconciliation. Orphan resolution requires successful scan evidence, explicit worker absence, and the recorded launch age.

Every runtime start re-reads the durable run and attempt immediately before launch. Missing or unreadable state, lost ownership, terminal run state, stop/cancel intent, a non-launching attempt, or a closed scheduler launch gate prevents spawning. An in-flight start is retained through cancellation rather than settled using an absent launch record.

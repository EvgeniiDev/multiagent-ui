## Исторический инцидент — триггер навсегда неатрибутируем (закрыт как evidence gap)

- **`U5 stop during a running check` упал в полном прогоне**
  `u1-u5-20261001-0501.log`: drive-timeout через 10.565 с, последнее
  состояние `run failed/verify val=failed/verify` ДО отправки stop.
  `echo start && sleep 60` при timeoutSec=90 истечь за это время не мог.
- Повторная прямая проверка полного исходного лога (237 строк) подтвердила:
  в нём нет `run.error`, `run.diagnostic`, procs/reports/events или любого
  различающего fingerprint; per-test state удалялся `after()`. Все пять
  исходных U5 source/test файлов сейчас untracked, поэтому incident-era
  diff восстановить нельзя. **Ретроспективная атрибуция закрыта навсегда:**
  нужных данных не сохранилось.
- Наблюдаемое окно ограничивается `[record_snapshot → proc-intent]`:
  `val.phase='verify'` пишет только `record_snapshot`. Однако корректная
  граница — **«leadered proc record не успел сохраниться»**, а не обязательно
  «intent не сохранился»: landed intent с подтверждённым spawn failure
  (`never_spawned`) также даёт тот же `failed/verify` без leader. Реальный
  случай с доказательством такого fingerprint не обнаружен.
- Ближайший подтверждённый механизм — CAS `revision_conflict` из-за
  конкуренции intent-send с 300-ms heartbeat. Он действительно встретился
  в production U7b (`run_8562b922`, журнал U7b row 49) с той же сигнатурой
  и явным fingerprint, но **не доказывает**, что именно он сработал 0501.
  Исправление CAS backoff уже внесено и проверено в U7b row 51.
- Fault matrix из 8 инъекций разделила наблюдаемые fingerprint-классы;
  34/34 последующих естественных probe завершились без повторения.
  Ни новый product fix, ни повторные нагрузочные прогоны не обоснованы.
  Существующие timeout dumps/incident probe остаются пассивной страховкой:
  будущее повторение должно сохранить `error`, `diagnostic`, proc proof,
  check reports и event tail.
- **Статус:** историческая причина `UNATTRIBUTABLE` (не «исправлена» и не
  приписана CAS); incident investigation закрыто. Это не принимает весь
  U5/Core: Compose/live runtime, managed boardctl/HTTP и прочие U7 DoD-гейты
  остаются отдельными обязательными условиями.

## Принятые семантические решения U5 (поздние)

- **Runner quiesce ≠ user-stop.** `sched.quiesce()` запрещает ВСЕ новые
  работы (begin_attempt/begin_validation/check-spawn, до и после intent),
  отменяет собственные check-группы через тот же kill/positive-proof путь,
  но НЕ резолвит reservation: validation остаётся 'active' с записанным
  владельцем. Истечение lease САМО по себе adoption не разрешает —
  наследник обязан принести положительное доказательство смерти
  владельца (process/env) или retirement оригинального окружения.
  User stop/cancel по-прежнему закрывает раунд
  'cancelled'; реально завершённый пайплайн всё ещё репортит 'settled'.
- **Quiesce-фенс на STOP-FENCE.** Проверка в `tryLaunch` дублируется
  непосредственно перед `runtime.start` (окно begin_attempt→start
  закрыто); отказ проходит через существующий never-entered reconcile —
  `resolve_attempt 'failed'` с причиной `launch never entered`.
- **driver.stop — один общий дедлайн.** `quiesce()` → `pump.stop(remaining)`
  → `scheduler.drain(remaining)`: суммарный bound =
  `MANAGED_STOP_DRAIN_MS` (15с), а не 2×. Drain — best-effort: grace-период
  контейнера (~10с) может убить процесс раньше; гарантированного drain
  НЕ заявляется. `pending > 0` логируется честно.
- **Detached-группы переживают выход Node на generic-хосте.** Комментарий
  «убиты при выходе» убран как ложный: смерть устанавливается только
  записанными kill-proof'ами или пробой наследника; live-группы после
  истечения bound — «last-recorded state», не «мертвы».
- **`ACP_EXEC_DIR` fail-closed.** Путь обязан иметь basename `execution`;
  `ACP_EXEC_DIR=/x/custom` — отказ (иначе токен/staging ушли бы в
  `<parent>/execution`, а Porch-стор — в `/x/custom` — тихий split-store).
  `STATE_DIR`+`ACP_EXEC_DIR` требуют точного соответствия.
- **`validationEnabled` — явное проксирование.** Старое `null` делегировало
  решение в `env` внутри фабрики и работало корректно; теперь разрешённый
  гейт передаётся явно, чтобы стартовая evidence-строка и реальный
  scheduler совпадали по построению, не по делегации.
- **Артефактная идентичность `stored`.** Физическое имя закоммиченного
  артефакта = значению `stored` (идентификатор записи, напр. `art_val_*`
  для validation-артефактов); логическое `file` может повторяться между
  раундами. `continuationFor` читает `stored ?? file` с проверкой
  байтов/hash/len; `cmdResolveAttempt` не перезаписывает immutable-записи;
  direct-API метаданные артефакта без байтов не создают проверяемый контент.
- **Managed boardctl — только API.** Managed `review` — read-only из
  run-агрегата; `accept`/`stop` — user-channel lifecycle-команды через
  `POST /api/execution/cards/:cardId/commands` (internal-токен НЕ
  используется; authenticated internal-канал — только у scheduler'а и
  импорта роль-evidence). Legacy `.acp/cards` review-check/verdict/move/
  claim/block/rm/set-stage/status на managed картах — явный отказ до
  любой записи; нелайфсайкл поля разрешены (server merge перекрывает
  protected-поля).
- **Роль-доказательства: `.acp-out` в pristine-копии.** Reviewer/checker
  пишут предписанный документ в СВОЮ копию; scheduler импортирует,
  проверяет байты/hash/round/resultSha256/role/attempt-binding и
  записывает immutable evidence через `record_report`. Промпты явно
  запрещают legacy `boardctl review --close/--round/--sync/review-check`
  на managed картах.
- **Journal-replay typed discharge.** `check_recorded`/terminal-replay
  не blanket-discharge: check-report требует typed-эквивалентности
  authoritative-записи + verified артефактных байтов (record id/kind/
  validationId/SHA); resolve требует полного результата (status/exit/
  duration/final/output bytes+SHA); `finalText` без staged-артефакта —
  owed-bytes реконструкция, не тихий discharge; настоящие transport-
  outage пробрасываются для retry (catch-`null` убран); settle-proof
  требует положительного child-доказательства (`childNone===true`
  аттестация), `null` никогда не «нет ребёнка».
- **scanPredecessors per-tick.** Predecessor, умерший ПОСЛЕ первого тика
  наследника, теперь наследуется; `seenPredecessors` ставится только
  после ENOENT/успешного чтения spool (EACCES/EIO ретраятся); consumed
  tracked-entries не воскрешаются одноразовым merge-сетом.

## Операционные примечания

- Сервисы/Compose НЕ стартовали в рамках U5; runner запущен только в
  in-process тестах. Токен internal API — `<stateDir>/execution/
  internal-token`, в env/логах/записях не появляется.
- Journal/spool/snapshot файлы — per-instance в `<stateDir>/execution/`;
  adopter читает предшественников по scanPredecessors; dead-letter только
  для неисправимо битых байтов/неизвестных kind.

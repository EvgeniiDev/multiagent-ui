# Правила тестирования ACP UI

Правила обязательны для изменений в этом репозитории. Цель — проверять пользовательский путь и фактически работающую сборку, а объём проверок выбирать по затронутому поведению.

## 1. Определить, что может сломаться

До изменения перечислить затронутые пользовательские действия, компоненты и зависимости: фронтенд, state, runner, мост, CLI/адаптер внутри образа. Для каждого существенного риска выбрать проверку с наблюдаемым результатом. Не ограничиваться списком изменённых файлов: изменение адаптера может сломать несколько вкладок без изменения UI.

Для правок только документации достаточно проверить содержание, ссылки и diff. Для изменения поведения нужны проверки соответствующего поведения. Полный дорогой прогон всех моделей требуется при изменении общего контракта режимов или выпуске всех режимов; локальная правка не требует автоматически повторять весь релизный набор.

## 2. Воспроизвести баг до исправления

Сохранить точные шаги, карточку/сессию, исходное состояние, URL и ответ с ошибкой. Различать ошибку JavaScript, HTTP, JSON-RPC, ответ приложения с отказом и отображаемый баннер. Найти причину на границе компонентов, прежде чем менять код.

Добавить регрессионную проверку, которая падает до исправления и проходит после него. Для чисто визуальной проблемы допустима воспроизводимая браузерная проверка с измерением стилей или снимком. Если заявленный сбой не воспроизведён, явно записать это; не выдавать исправление другого симптома за доказанное устранение исходного сбоя.

## 3. Проверять обычные данные и переходы состояния

Специальные тестовые карточки дополняют проверку существующих карточек. Для изменённого пути включения/загрузки обязательны следующие случаи:

| Состояние | Что проверить |
|---|---|
| Существующая неподключённая карточка | Правильная кнопка, один запрос включения, успешный переход |
| Уже подключённая карточка | При открытии нет предложения включить режим повторно |
| Ответ сервера ещё не пришёл | Понятное ожидание, никаких действий на основе неизвестного состояния |
| Ошибка или недоступность сервера | Видимая причина, отсутствие ложного успеха, возможность восстановиться |
| Карточка закрыта или переключена во время запроса | Старый ответ не меняет другую карточку |
| Повторный клик | Нет второго независимого запуска или скрытого повторного POST |
| Повторное открытие и обновление страницы | Сохранённое состояние корректно восстанавливается |

Намеренно задержать ответ, чтобы увидеть промежуточное состояние. Для браузерного подтверждения server truth можно задержать настоящий ответ; подменённый успешный DTO не является проверкой продового backend.

Не запускать работу на пользовательской карточке ради теста без разрешения на этот запуск. Проверять открытие и чтение без изменения данных; для запусков использовать согласованную карточку или отдельную помеченную тестовую карточку. Сохранять чужие карточки, проекты, документы и активные прогоны.

## 4. Проверять UI в браузере

SSR и успешная сборка не доказывают правильность дизайна. Открыть изменённый экран через реальные элементы навигации и проверить начальное состояние, ожидание, успех и ошибку. Проверять доступность нужных действий, их подписи и видимый результат.

Для изменения элементов управления проверить соответствие существующим компонентам/токенам: размеры, шрифт, цвет, границы, hover, focus, disabled и узкий экран. Проверить вложенные компоненты отдельно: родительский scoped CSS может до них не доходить.

Контролировать одновременно pageerror, неуспешные HTTP/JSON-RPC ответы и пользовательские баннеры. Ноль pageerror не означает исправный интерфейс. Для ожидаемого отказа, например GET404 неподключённой карточки, подтвердить правильную обработку; не игнорировать все ошибки этого статуса или весь журнал.

## 5. Проверять восстановление и параллельные сессии

При изменении моста, адаптера или восстановления проверить одну сессию, две разные сессии одновременно и одновременное открытие одной сессии в двух окнах. Загрузка одной сессии не должна завершать процесс другой. Проверить восстановление после подтверждённого завершения собственного процесса.

Проверить маршрутизацию истории и событий, независимость request-id и разрешений, сохранение правильной карточки/сессии. История чужой сессии не должна попасть в другую вкладку. Следовать существующим инвариантам bridge из AGENTS.md.

Дождаться завершения восстановления. Успешное открытие WebSocket или исчезновение старого текста ошибки недостаточно: session/load должен успешно завершиться, а финальный интерфейс — выйти из ожидания. Записать измеренное время. При ошибке сохранить конкретную причину; очищать её после подтверждённого восстановления.

## 6. Доказывать поведение режимов на соответствующем уровне

При изменении подготовки идеи проверить реальный путь: обсуждение/прожарка → ответы и продолжение → требования → согласование точной версии → план, связанный с требованиями → согласование → готовность к передаче. Проверить содержимое и привязку к нужной карточке. Генерация файла сама по себе не доказывает заполнение карточки и готовность плана.

При изменении конкретного режима разработки проверить его изменённый путь запуска, события, ожидаемые пользовательские решения и итог. При выпуске всех режимов подтвердить Fusion, Orchestrator и Swarm отдельно, с настоящими вызовами провайдеров и фактическим результатом/проверками в рабочем каталоге. Успешный тест одного режима не переносится автоматически на остальные.

Моки допустимы в автоматизированных тестах. В отчёте явно различать unit/contract, браузер с подменами и браузер с настоящим backend/провайдером. Не называть мок успешным продовым запуском. Для сценария чтения или UI-правки не запускать платные модели без необходимости.

## 7. Проверять фактическую выкладку

Перед утверждением «раскатано» подтвердить на адресе пользователя:

- checkout/ветку и commit, из которых выполняется выкладка;
- реальный bind mount или путь сервиса и обслуживаемый хэш frontend asset;
- ID работающих Docker-образов изменённых сервисов;
- версии и необходимые патчи CLI/адаптеров внутри работающего контейнера;
- фактические флаги и доступность изменённых возможностей через API и UI.

Изменение Dockerfile или установленного пакета требует сборки и обновления соответствующего контейнера; перезапуск state не обновляет Pi-мост. Изменение исходников фронтенда требует host build. Выполнять только необходимые операции Compose по правилам AGENTS.md, сохраняя владельцев портов и незатронутые сервисы.

После последней выкладки повторить затронутый пользовательский путь в настоящем браузере на адресе пользователя. Проверить свежую загрузку и сценарий сохранённого состояния. Если открытым страницам нужен reload, сказать об этом в итоговом сообщении.

## 8. Ограничивать вывод собранными доказательствами

В итоговом отчёте указать: что изменено, какие проверки выполнены, что действительно подтверждено на проде и какие ограничения остались. Для существенного релиза сохранить краткий отчёт с командами, результатами, commit/образами и ссылками на доказательства. Не сохранять токены, auth-файлы и секреты в отчётах или снимках.

Нельзя объявлять задачу завершённой только по числу зелёных тестов, сообщению субагента, сборке или отсутствию JS-ошибок. Ответственный за итоговую интеграцию проверяет общую ветку, фактическую выкладку и пользовательский путь самостоятельно.

После успешных проверок не повторять их без причины. Повтор требуется при новом изменении затронутого поведения, другой сборке/выкладке, новой ошибке или оставшемся сомнении. Сбой в собственном тестовом инструменте исправить и отделить от сбоя продукта.

Основание правил: [разбор ошибок панели и Pi-сессий от 4 октября 2026](docs/reports/managed-panel-followup-20261004.md).
